# 다중 에이전트 확장 (multi-agent)

> **먼저 읽어라 — 이 파일은 가장 마지막에 도달하는 계층이다.**
> 논문 §XI(결정 프레임워크) Table XII는 두 줄을 못 박는다. **출력 품질 편차**에는 계산적 센서(린터·타입체커·테스트)에서 시작하고 **다중 에이전트 리뷰는 아직 추가하지 마라.** **에이전트 무한 루프**에는 재시도 한도와 타임아웃에서 시작하고 **복잡한 오케스트레이션은 아직 추가하지 마라.** 여기 적힌 것은 **더 단순한 계층을 먼저 시도해 본 뒤에** 손대는 영역이다. 다만 이것은 차단 게이트가 아니다 — 팀·오케스트레이터 생성은 요청받는 즉시 수행한다(`SKILL.md` 4단계). 성숙도 조건은 **무인 운영 승격**에만 걸리며, 실행의 산물을 실행의 전제조건으로 걸지 않는다. 하네스 없이 에이전트만 늘리면 실패가 병렬화될 뿐이고, 그것이 논문 §XIV(한계)가 말한 "안전으로 위장한 병목"이다.
> **진입 판별 질문:** 이 문제는 에이전트를 하나 더 늘려야 풀리는가, 아니면 센서를 하나 더 붙이면 풀리는가? 후자면 이 파일을 닫고 `layers.md`의 L2로 돌아간다.

**라우팅.** 팀 모드(`TeamCreate`/`SendMessage`)로 설계할 때만 `multi-agent-team.md`를 읽어라. 서브에이전트 모드는 이 파일로 충분하다. 이 파일은 모드와 무관한 규범(경계 장치·아키텍처 패턴·핸드오프·검증자 독립·공유 상태·에러 핸들링·에스컬레이션)과 서브 에이전트 모드의 실행 방법을 담고, 팀 전용 내용(팀 크기·팀 통신·팀 오케스트레이터 템플릿·하이브리드)은 전부 `multi-agent-team.md`에 있다.

## 1. 적용 전제 — 경계로 확장되는 하네스

논문 §XVII(다중 에이전트): 6계층은 개별 에이전트에 적용된다. 여러 에이전트가 협업하면 하네스는 **에이전트 사이의 경계**로 확장된다. 각 에이전트가 자기 가이드·센서·권한을 갖는 것에 더해, 시스템은 다섯 가지 경계 장치를 요구한다. 다섯이 모두 빠진 구성은 협업이 아니라 컨텍스트 오염이다. 설계 전에 각 행마다 "우리 구성에서 이것은 어디에 구현되어 있는가"를 답할 수 있어야 한다.

## 2. 실행 모드 3종과 선택 순서

| 모드 | 언제 쓰는가 | 실행 수단 | 제약 |
|---|---|---|---|
| **에이전트 팀** (기본) | 2명 이상 협업, 실시간 조율·교차 검증·상충 토론이 품질을 좌우 | `TeamCreate` + `SendMessage` + `TaskCreate`/`TaskUpdate` 자체 조율 — **상세는 `multi-agent-team.md`** | 세션당 1팀만 활성 / 중첩 불가(팀원은 팀 생성 불가) / 리더 이전 불가 / 토큰 비용 높음 |
| **서브 에이전트** (경량) | 결과 전달만 필요, 팀 통신 오버헤드가 이득보다 클 때 | `Agent(prompt, subagent_type, model, run_in_background)` — 상세는 본 문서 13절 | 서브끼리 통신 불가 / 메인이 모든 조율 담당 / 실시간 도전 불가 |
| **하이브리드** | Phase마다 성격이 확연히 다를 때 | Phase 단위로 팀/서브를 섞고 각 Phase 상단에 모드 명시 — 상세는 **`multi-agent-team.md` 6절** | 모드 전환 지점에서 데이터가 끊기기 쉬움 |

**의사결정 순서:** (1) 2명 이상이면 **먼저 팀으로 설계 가능한지** 검토한다 — 발견 공유·상충 토론·누락 보완이 단독 실행 대비 품질을 올리기 때문이다. (2) 팀 통신이 구조적으로 불필요하고 오버헤드가 이득보다 크면 서브 에이전트. (3) Phase별 성격이 확연히 다르면 하이브리드.
```
에이전트가 2개 이상인가?
├── Yes → 에이전트 간 통신이 필요한가?
│         ├── Yes → 에이전트 팀 (기본값)
│         └── No  → 서브 에이전트 (생성-검증, 전문가 풀 등 결과 전달형)
└── No (1개) → 서브 에이전트
```
> **팀 모드의 이점은 "조율"이지 "컨텍스트 공유"가 아니다.** 팀을 골랐다고 대화를 공유하는 것이 아니다. 산출물은 언제나 `_workspace/` 파일로 흐르고 `SendMessage`는 조율 신호만 나른다(본 문서 10절). Phase마다 다른 조합이 필요할 때의 **팀 재구성** 절차는 `multi-agent-team.md` 2절.

> **팀을 골랐다면 여기서 `multi-agent-team.md`로 간다.** 팀 크기·통신 프로토콜·오케스트레이터 템플릿 A·하이브리드 템플릿 C가 그 파일에 있다. 서브 에이전트 모드면 이 파일만으로 끝난다 — 3절 이후를 그대로 이어 읽고 13절 템플릿을 쓴다.

## 3. 아키텍처 패턴 6종
### 3.1 파이프라인 — 순차 흐름, 이전 출력이 다음 입력
```
[분석] → [설계] → [구현] → [검증]
```
**적합:** 각 단계가 이전 산출물에 강하게 의존 · **예시:** 소설 — 세계관→캐릭터→플롯→집필→편집 · **주의:** 병목 하나가 전체를 지연시키므로 각 단계를 가능한 한 독립 설계 · **모드:** 순차 의존이 강해 팀의 이점이 제한적. 내부에 병렬 구간이 있으면 팀이 유용.
### 3.2 팬아웃/팬인 — 병렬 처리 후 통합
```
         ┌→ [전문가A] ─┐
[분배] → ├→ [전문가B] ─┼→ [통합]
         └→ [전문가C] ─┘
```
**적합:** 같은 입력에 서로 다른 관점·영역 분석이 필요 · **예시:** 종합 리서치 — 공식/미디어/커뮤니티/배경 동시 조사 · **주의:** 통합 단계 품질이 전체 품질을 결정 · **모드:** 팀의 가장 자연스러운 패턴. 한 에이전트의 발견이 다른 에이전트의 조사 방향을 실시간으로 바꿀 수 있어 향상 폭이 가장 크다.
### 3.3 전문가 풀 — 상황에 맞는 전문가만 선택 호출
```
[라우터] → { 전문가A | 전문가B | 전문가C }
```
**적합:** 입력 유형에 따라 처리가 달라짐 · **예시:** 코드 리뷰에서 보안/성능/아키텍처 중 해당 영역만 · **주의:** 라우터 분류 정확도가 핵심. 분류 실패를 잡을 센서가 없으면 조용히 틀린 전문가에게 간다 · **모드:** 서브 에이전트. 필요한 전문가만 부르므로 상시 팀이 불필요.
### 3.4 생성-검증 — 생성자와 검증자가 쌍으로 동작
```
[생성] → [검증] ──실패 증거──→ [라우터] → [생성] 재실행 (예산 내)
```
**적합:** 품질 보장이 중요하고 객관적 검증 기준이 존재 · **예시:** 웹툰 — artist 생성 → reviewer 검수 → 문제 패널 재생성 · **필수:** 재시도 상한을 `maxTurns`로 강제한다(본 문서 7절). 기본값과 그 근거는 `layers.md` L3 한 곳에만 있다 — 여기서 숫자를 다시 정하지 마라. 예산 소진 시 강제 통과가 아니라 미검증 표식 + 에스컬레이션(본 문서 12절) · **필수:** 검증자는 생산자와 분리되고 쓰기 권한이 없다(본 문서 8절).
### 3.5 감독자 — 상태를 보며 동적으로 작업 분배
```
         ┌→ [워커A]
[감독자] ─┼→ [워커B]   ← 진행 상황을 보고 다음 배치를 배정
         └→ [워커C]
```
**적합:** 작업량이 가변적이거나 런타임에 분배를 정해야 함 · **예시:** 대규모 코드 마이그레이션 · **팬아웃과의 차이:** 팬아웃은 사전 고정 분배, 감독자는 진행 기반 동적 조정 · **주의:** 감독자가 병목이 되지 않게 위임 단위를 크게 · **모드:** 공유 작업 목록의 자체 요청(claim)이 이 패턴과 그대로 맞물린다.
### 3.6 계층적 위임 — 재귀적 분해
```
[총괄] → [팀장A] → [실무자A1] / [실무자A2]
       → [팀장B] → [실무자B1]
```
**적합:** 문제가 자연스럽게 계층으로 분해됨 · **예시:** 풀스택 앱 — 총괄 → 프론트팀장(UI/로직/테스트) + 백엔드팀장(API/DB/테스트) · **주의:** 깊이 3단계 이상은 지연과 컨텍스트 손실이 급증하므로 2단계 이내 · **모드:** 팀은 중첩 불가. 1단계는 팀, 2단계는 서브로 구현하거나 평탄화해 단일 팀으로.

## 4. 복합 패턴

| 복합 패턴 / 시나리오 | 구성·권장 모드 | 이유·예시 |
|---|---|---|
| 팬아웃 + 생성-검증 | 병렬 생성 후 각각 독립 검증 | 다국어 번역 — 4개 언어 병렬 → 각각 네이티브 리뷰어 |
| 파이프라인 + 팬아웃 | 순차 중 일부를 병렬화 | 분석(순차) → 구현(병렬) → 통합 테스트(순차) |
| 감독자 + 전문가 풀 | 감독자가 전문가를 동적 호출 | 고객 문의 — 분류 후 적합한 전문가 할당 |
| 리서치 + 분석 | 에이전트 팀 | 조사자 간 발견 공유, 상충 정보 실시간 토론 |
| 설계 + 구현 + 검증 | 에이전트 팀 | 설계자↔구현자 피드백 루프 (검증자는 본 문서 8절에 따라 분리·읽기 전용) |
| 감독자 + 워커 | 에이전트 팀 | 공유 작업 목록 동적 할당, 워커 간 진행률 공유 |
| 생성 + 검증 (2인) | 서브 에이전트 | 결과 전달이 핵심이고 검증자 독립을 보장하기 쉽다 |

## 5. 분리 기준과 중복 검토·재사용 설계

| 분리 기준 | 분리 | 통합 |
|---|---|---|
| 전문성 | 영역이 다르면 분리 | 영역이 겹치면 통합 |
| 병렬성 | 독립 실행 가능하면 분리 | 순차 종속이면 통합 고려 |
| 컨텍스트 | 컨텍스트 부담이 크면 분리 | 가볍고 빠르면 통합 |
| 재사용성 | 다른 팀에서도 쓰면 분리 | 이 팀에서만 쓰면 통합 고려 |

**중복 검토는 신규 생성 전에 반드시 한다.** 하네스를 반복 구축하면 역할이 겹치는 에이전트·스킬이 다른 이름으로 누적된다. 신규 에이전트 전에는 `.claude/agents/`를, 신규 스킬 전에는 `.claude/skills/`를 훑는다. 하나의 에이전트가 하나의 역할에 집중할수록 재사용성이 높고 중복이 준다. **기존 에이전트를 일반화할 때는** 그에 의존하는 오케스트레이터·팀 구성의 동작이 바뀔 수 있으므로, 확장 전 의존성을 확인하고 확장 후 드라이런으로 기존 동작 유지를 확인한다.

| 상황 | 조치 |
|---|---|
| 기존이 신규 역할을 **완전히 포함** | 신규 생성 금지 — 기존 재사용 |
| 기존이 **부분 포함**이고 일반화 가능 | 기존을 일반화하여 확장 |
| 도메인 특화가 의도된 부분 포함 | 신규 생성 진행 — 별개로 유지 |
| 역할 범위가 완전히 다름 | 신규 생성 진행 (역할이 둘 이상이면 분리 가능성을 먼저 본다) |

## 6. 에이전트 타입과 모델 선택

| 빌트인 타입 | 도구 접근 | 적합한 용도 | 커스텀 타입을 쓸 때 |
|---|---|---|---|
| `general-purpose` | 전체 (WebSearch·WebFetch 포함) | 웹 조사, 범용 작업 | 역할이 복잡하고 여러 세션에서 재사용될 때 |
| `Explore` | 읽기 전용 (Edit/Write 없음) | 코드베이스 탐색·분석·리뷰 — 실수로 파일을 고치는 것을 구조적으로 차단 | 파일 수정이 필요한 구현 작업일 때 |
| `Plan` | 읽기 전용 (Edit/Write 없음) | 아키텍처 설계·계획 — 분석에 집중, 코드 변경 방지 | 필요한 도구만 열고 전문 지시를 담아야 할 때 |

**빌트인 타입을 쓰더라도 `.claude/agents/{name}.md` 정의 파일은 반드시 만든다.** 정의 파일 없이 `Agent`의 prompt에 역할을 통째로 넣는 것은 금지한다. (a) 파일로 존재해야 다음 세션에서 재사용된다 (b) 핸드오프·통신 프로토콜이 명시되어야 협업 품질이 보장된다 (c) 하네스의 핵심 가치가 에이전트(누가)와 스킬(어떻게)의 분리다. 빌트인 타입은 `subagent_type`으로 지정하고, 정의 파일에는 역할·원칙·프로토콜·경계를 담는다.

**모델 규범 — 작업에 맞는 최소 모델이 기본이고, 상위 모델은 사유를 명시할 때만 쓴다.** 논문 Table II는 **모델을 고정한 채 하네스만 바꿔** GAIA 30.91%→74.55%(+43.64pt)를 얻었다. 품질을 만드는 것은 모델 등급이 아니라 하네스다. 상위 모델 일괄 강제는 논문 §VIII(관찰가능성)의 "검증된 결과당 비용" 지표와 정면으로 충돌한다.

- **다만 `model` 파라미터는 모든 `Agent` 호출과 모든 팀원 정의에 명시한다.** 강제되는 것은 특정 모델이 아니라 **명시성**이다. 명시되지 않은 모델은 관측도 비용 귀속도 되지 않는다(논문 §VIII(관찰가능성) "비용 귀속은 일별이 아니라 작업별로"). 상위 모델에 승인 게이트가 필요하면 `permissions.ask: ["Agent(model:opus)"]`를 건다. 문법과 우선순위는 `enforcement.md` 참조.

## 7. 에이전트 정의 파일 구조와 루프 경계

위치: `프로젝트/.claude/agents/{agent-name}.md`. frontmatter의 제약 필드는 논문 Table IV의 루프 경계를 실제로 강제하는 몇 안 되는 수단이다. 특히 `maxTurns`는 **"단계당 최대 재시도 3회"의 유일한 네이티브 강제 수단**이다.

| frontmatter 필드 | 무엇을 경계 짓는가 |
|---|---|
| `tools` / `disallowedTools` | 사용 가능 도구 화이트리스트 / 명시적 차단 (최소 권한) |
| `permissionMode` | 승인 정책. 검증자에는 `dontAsk` 권장(본 문서 8절) |
| `model` / `effort` | 모델·추론 예산 명시 — 비용 귀속과 관측의 전제 |
| `maxTurns` | **재시도·턴 상한. Table IV "재시도 3회"의 유일한 네이티브 강제** |
| `hooks` / `memory` / `isolation: worktree` | 도구 호출 전후 강제 검사 / 세션 간 지속 컨텍스트 / 격리 워크트리로 폭발 반경 축소 |

> 각 필드의 정확한 문법·우선순위·조합 규칙은 `enforcement.md`에 있다. 여기서 반복하지 않는다.

**필수 섹션:** 핵심 역할 / 작업 원칙 / 입력·출력 프로토콜 / 핸드오프 / 에러 핸들링 / 협업. 팀 모드면 **팀 통신 프로토콜**을 추가한다 — 그 절의 작성법(발신·수신·브로드캐스트 대상)은 `multi-agent-team.md` 4절. 작업 원칙은 관찰 가능한 기준으로 쓴다 — "철저히 조사하라"가 아니라 "명명된 출처 3곳 이상 인용, 미확인 항목은 미해결 필드에 기재". 골격의 실제 인스턴스는 2건이다 — 검증자 전문은 본 문서 15절, 생산자(팀 통신 프로토콜 포함) 전문은 `multi-agent-team.md` 8절.

## 8. 검증자 독립 원칙

논문 §XVII(다중 에이전트): **아티팩트를 생산한 에이전트가 그 품질의 유일한 심판이어서는 안 된다. 생산자 편향은 실재한다.** 자기가 만든 것을 자기가 통과시키는 구조는 센서가 아니라 자기 확인이다.

1. **가능하면 결정적 센서를 먼저 쓴다.** 린터·타입체커·테스트·스키마 검증으로 판정 가능한 것에 검증자 에이전트를 붙이지 않는다(논문 §IV(센서) "계산적 센서 우선"). 실질적 판단이 필요한 작업에만 별도 검증자를 둔다.
2. **검증자는 출력을 조용히 다시 쓰지 않고 실패를 보고한다.** 그래서 검증 에이전트 정의는 `tools`에서 **Edit/Write를 제외**하고 `permissionMode: dontAsk`를 권장한다. 쓰기 권한이 없으면 "고쳐놨습니다"라는 보고 자체가 불가능해지고 실패가 반드시 증거로 표면화된다.
3. **라우터가 되돌린다.** 검증자는 실패 증거를 라우터(오케스트레이터)에게 반환하고, 라우터가 그 증거를 생산자에게 되돌린다. 재시도 예산(`maxTurns`)이 소진되면 **에스컬레이션**한다(본 문서 12절).
4. **강제 통과 금지.** 예산 소진 시 산출물에 **미검증 표식**을 붙이고 무엇이 검증되지 않았는지 명시한다. 유창한 최종 보고 뒤에 부분 실패를 숨기지 않는다(논문 §V(에이전틱 루프)).

> 검증자가 "다 좋아 보입니다"만 반환하고 실패를 한 번도 낸 적이 없다면 그 검증자를 의심하라. 매 실행 100% 통과하는 센서 스위트는 논문 §XIV(한계)가 명시한 위험 신호다.

## 9. 타입 있는 핸드오프 — 5필드 + 미해결

논문 §XVII(다중 에이전트): A→B 전달은 자유 형식 요약이 아니라 **타입 인터페이스**여야 한다. **"완료, 좋아 보임" 같은 요약은 프로덕션 워크플로를 전진시켜서는 안 된다.** 수신자가 아티팩트를 직접 열어 독립 검증할 수 있어야 한다. **미해결 항목이 하나라도 있으면 그 항목은 최종 보고서에 그대로 올라간다** — 중간에서 사라지면 그것이 논문 §V(에이전틱 루프)가 금지한 부분 실패 은닉이다.

**필드 구성:** 논문 §XVII(다중 에이전트) A항이 못 박은 5필드는 작업 정체성·아티팩트 포인터·증거·가정·**기한(deadline)**이다. 같은 절이 별도로 요구하는 "무엇이 미해결로 남았나"를 이 하네스는 **6번째 필드로 분리**한다. 기한과 미해결을 한 칸에 합치면 둘 중 하나가 반드시 사라지고, 실제로 사라지는 쪽은 늘 기한이다 — 그러면 Table IV의 벽시계 예산(단계당 30분)이 에이전트 경계를 넘어 전파될 통로가 없어진다.

| # | 필드 | 담는 것 | 비면 생기는 일 |
|---|---|---|---|
| 1 | 작업 정체성 | 어떤 작업의 어느 단계인가, 실행 id | 어느 실행의 산출물인지 추적 불가 |
| 2 | 아티팩트 포인터 | 준비된 산출물의 **정확한 경로** | 수신자가 요약만 믿고 원본을 못 연다 |
| 3 | 증거 | 무엇을 어떤 센서로 검증했나 (명령·결과) | "좋아 보임"이 검증을 대체한다 |
| 4 | 가정 | 어떤 전제 위에서 만들었나 | 하류에서 조용히 깨진다 |
| 5 | **기한(deadline)** | 이 산출물이 **언제까지** 처리돼야 하는가 (남은 벽시계 예산·후속 단계의 마감 시각) | 상류의 시간 예산이 하류로 전파되지 않아 각 단계가 무한정 늘어진다 |
| 6 | 미해결 | 무엇이 **미해결**로 남았나 | 부분 실패가 유창한 요약 뒤에 숨는다 |

```markdown
## HANDOFF
- 작업 정체성: {task_id} / {phase} / {from-agent} → {to-agent}
- 아티팩트 포인터: `_workspace/02_researcher_findings.md` (신규) / `_workspace/01_input_spec.md` (참조, 미변경)
- 증거: `npm test` → 통과(42 passed) / 스키마 검증 `validate.py` → 통과 / 출처 12건 중 12건 URL 확인
- 가정: 입력 데이터 기준 시점은 {날짜}로 가정 / {X}는 기본값 사용 — 사용자 확인 없음
- 기한: 통합 단계 시작까지 남은 예산 12분 / 이 작업의 전체 상한 30분 중 18분 소진
- 미해결: {Y} 영역 접근 실패로 미수집(재시도 1회 후 중단) / {Z}는 상충 정보 2건 병기 — 판정 필요
```

> **「핸드오프」와 「실패 보고」를 같은 이름으로 부르지 마라.** 핸드오프는 **생산자 → 수신자**(다음 단계 에이전트 또는 라우터)의 전달 포맷이고 위 6필드를 쓴다. 검증자가 내는 것은 **실패 보고**이며 **검증자 → 라우터** 방향의 다른 포맷(검사 대상·기대·실제·재현·실패 클래스·제안 수정 계층 6필드)이다 — `verifier-agent.md` 7절. 두 포맷은 필드 수가 같을 뿐 목적도 방향도 다르다. 검증자가 핸드오프 필드를 쓰면 "증거" 칸에 자기 판정을 적게 되고, 그 순간 생산자 편향이 다시 들어온다.

## 10. 공유 상태 모델과 데이터 전달 프로토콜

논문 §XVII(다중 에이전트): **여러 에이전트가 대화를 공유하면 컨텍스트 오염이 생긴다.** 각자의 추론·에러·교정이 다른 모두의 컨텍스트를 채운다. 더 나은 패턴은 구조화된 상태를 공유하고 **현재 작업에 관련된 상태만** 읽는 것이다. 워커는 공유 상태에 읽고 쓰고, 오케스트레이터의 컨텍스트는 깨끗하게 유지된다. 이 하네스에서 공유 상태는 **`_workspace/` 하나**다.
```
{project}/_workspace/
├── {phase}_{agent}_{artifact}.{ext}   ← 산출물 아티팩트. 예: 01_analyst_requirements.md
└── harness.md                          ← 체크포인트 / 래칫 원장 / 성숙도 (layers.md 참조)
```
- 파일명 규약 `{phase}_{agent}_{artifact}.{ext}`를 지킨다. 단계·생산자·산출물 종류가 경로만으로 판별되어야 라우터가 컨텍스트를 오염 없이 선택적으로 읽는다.
- **산출물 아티팩트는 보존**한다(사후 검증·감사 추적). **체크포인트는 활성 작업당 최신 1개만** 유지한다 — 덮어쓰기가 곧 만료다. 낡은 체크포인트가 없어진 파일과 번복된 결정을 가리키는 것이 논문 §XIV(한계)의 대표적 실패다. 경로는 항상 `_workspace/` 기준으로 명시한다. 세션 cwd를 따라가는 상대 경로 표현은 쓰지 않는다.

| 전략 | 방식 | 적용 모드 | 무엇에 쓰는가 |
|---|---|---|---|
| **파일 기반** | 약속된 `_workspace/` 경로에 쓰고 읽음 | 팀 + 서브 | **모든 산출물·증거·핸드오프의 기본 통로** |
| **태스크 기반** | `TaskCreate`/`TaskUpdate`로 작업 상태 공유 | 팀 | 진행 상황, 의존 관계, 작업 자체 요청(claim) — 상세 `multi-agent-team.md` 3절 |
| **메시지 기반** | `SendMessage`로 팀원 간 직접 통신 | 팀 | **조율 신호에 한정** — "X 완료, 경로는 여기", "Y 상충 발견, 확인 바람". 상세 `multi-agent-team.md` 3절 |
| **반환값 기반** | `Agent` 도구의 반환 메시지 | 서브 | 파일 포인터 + 핸드오프 6필드 요약. 본문 전체를 반환하지 않는다 |

**권장 조합(정정됨).** 서브 모드: 파일 기반(산출물) + 반환값 기반(포인터와 핸드오프 요약). 팀 모드의 조합(파일 + 태스크 + 메시지)과 세 통로의 역할 분담은 `multi-agent-team.md` 3절. **공통 금지:** 산출물 본문을 메시지나 반환값으로 실어 나르지 않는다. 그러면 모든 수신자의 컨텍스트가 남의 중간 추론으로 채워지고, 그것이 정확히 논문 §XVII(다중 에이전트)가 경고한 오염이다.

## 11. 에러 핸들링 규범

오케스트레이터와 각 에이전트 정의에 아래 세 문장을 규범으로 넣는다. 논문 §V(에이전틱 루프) "유창한 최종 답변 뒤에 부분 실패를 숨겨서는 안 된다"의 구현이다.

1. **에이전트 1개 실패 시 1회 재시도한다. 재실패하면 그 결과 없이 진행하고 보고서에 누락을 명시한다.** 단, **재시도해도 결과가 달라지지 않는 실패(권한 거부·인증 없음·입력 스키마 오류·비가역 차단)는 재시도 없이 즉시 라우터로 올린다.** 이런 실패에 재시도 예산을 쓰면 같은 거부를 두 번 받고 예산만 태운다 — 필요한 것은 다른 시도가 아니라 인간의 결정이다.
2. **상충하는 데이터는 삭제하지 않고 출처를 병기한다.** 판정 근거 없는 임의 선택은 조용한 데이터 손실이다.
3. **타임아웃 시 현재까지 수집된 부분 결과를 사용하고 미수집 영역을 명시한다.**

| 상황 | 전략 |
|---|---|
| 팀원 1명 실패·중지 | 유휴 알림 수신 → `SendMessage`로 상태 확인 → 재시작 또는 작업 재할당 |
| 재시도해도 안 바뀌는 실패(권한 거부·인증 없음·스키마 오류) | **재시도 생략.** 예산을 소모하지 않고 즉시 라우터 → 에스컬레이션 패킷 |
| 팀원 과반 실패 | 사용자에게 알리고 진행 여부 확인 |
| 팀원 간 데이터 충돌 | 출처 병기, 삭제 금지 |
| 작업 상태 지연 | 리더가 `TaskGet` 확인 후 `TaskUpdate`로 수동 갱신 |
| 재시도 예산 소진 | 강제 통과 금지 — 미검증 표식 + 에스컬레이션(본 문서 12절) |

## 12. 에스컬레이션 패킷 5요소

논문 §V(에이전틱 루프): **에스컬레이션은 실패가 아니다. 올바르게 에스컬레이션하는 에이전트가 자신만만한 오답을 내는 에이전트보다 가치 있다.** 다만 "막혔습니다"는 에스컬레이션이 아니다. 인간이 즉시 결정할 수 있는 형태여야 한다.

```markdown
## ESCALATION
- 필요한 결정: {인간이 무엇을 정해야 하는가 — 한 문장, 선택지 형태}
- 권장안: {에이전트의 추천과 근거 1~2줄}
- 이미 시도한 대안: 1) {시도} → {결과/실패 사유}  2) {시도} → {결과/실패 사유}
- 대기 비용: {지금 멈추면 무엇이 지연·낭비되는가}
- 응답 없을 때의 기본 조치: {가장 안전한 기본값과 그것이 안전한 이유}
```
다중 에이전트에서 에스컬레이션 주체는 **라우터(오케스트레이터)** 다. 워커가 개별적으로 인간을 호출하면 승인 요청이 난립해 논문 §VIII(관찰가능성)의 에스컬레이션률 지표가 무의미해진다. 워커는 라우터에 패킷을 올리고 라우터가 병합해 한 번에 올린다. "응답 없을 때의 기본 조치"가 비가역 행동이면 그 자체가 설계 오류다 — 기본 조치는 항상 되돌릴 수 있어야 한다.

## 13. 오케스트레이터 템플릿 — 서브 에이전트 모드

오케스트레이터는 팀 전체를 조율하는 상위 스킬이자 **라우터**다. 13.1(컨텍스트 확인)과 13.2(준비)는 **전 모드 공통**이며 팀 템플릿도 이 두 절을 그대로 참조한다. 13.3이 서브 에이전트 모드의 본체다. **팀 모드 템플릿 A와 하이브리드 템플릿 C는 `multi-agent-team.md` 5·6절에 있다.**

### 13.1 Phase 0: 컨텍스트 확인 (후속 작업 지원) — 전 모드 공통

`_workspace/` 존재 여부로 3분기한다. **미존재** → 초기 실행, Phase 1로. **존재 + 부분 수정 요청** → 부분 재실행. 해당 에이전트만 재호출하고 수정 대상 산출물만 덮어쓴다(이전 산출물 경로를 프롬프트에 포함해 기존 결과를 읽고 피드백을 반영시킨다). **존재 + 새 입력** → 새 실행. 기존을 `_workspace_{YYYYMMDD_HHMMSS}/`로 이동 후 Phase 1.

### 13.2 Phase 1: 준비 — 전 모드 공통

사용자 입력 분석 → `_workspace/` 생성 → 입력을 `_workspace/00_input/`에 저장.

### 13.3 템플릿 B — 서브 에이전트 모드

Phase 0(컨텍스트 확인 3분기)과 Phase 1(준비)은 13.1·13.2와 같다. frontmatter의 `name`은 `{domain}-orchestrator`, `description`에는 초기 실행 키워드와 후속 작업 키워드를 함께 넣는다(본 문서 14절). Phase 2에서 단일 메시지로 N개 `Agent`를 동시 호출한다.

| 에이전트 | subagent_type | 입력 | 출력 | model | run_in_background |
|---|---|---|---|---|---|
| {agent-1} | {타입} | {소스} | `_workspace/{phase}_{agent}_{artifact}.md` | {최소 모델} | true |

Phase 3: 반환값(파일 포인터 + 핸드오프 6필드) 수집 → 파일 산출물 `Read` → **독립 검증 서브 에이전트**(Edit/Write 없음) 호출 → 통합. Phase 4: 산출물 보존, 결과 요약 보고.

**작성 원칙:** (1) 실행 모드를 최상단에 명시하고 하이브리드면 Phase별 모드 표를 붙인다. (2) 팀 모드는 `TeamCreate`/`SendMessage`/`TaskCreate` 사용법을, 서브 모드는 `Agent` 파라미터(`subagent_type`·`prompt`·`model`·`run_in_background`)를 완전히 적는다. (3) 파일 경로는 `_workspace/` 기준으로 명확히, 상대 경로 표현 금지. (4) Phase 간 의존성을 명시하고 하이브리드는 전환 지점을 강조한다. (5) 에러 핸들링은 "모두 성공한다"고 가정하지 않는다.

## 14. 후속 작업 지원

후속 지원이 없으면 하네스는 첫 실행 후 사실상 죽은 코드가 된다. 세 가지를 반드시 넣는다.

1. **description에 후속 작업 키워드를 포함한다.** 초기 실행 키워드만으로는 두 번째 요청에서 트리거되지 않는다. 포함할 표현: 재실행/다시 실행/업데이트/수정/보완, "{도메인}의 {부분}만 다시", "이전 결과 기반으로", "결과 개선", 그리고 도메인의 일상 어휘.
2. **Phase 0의 `_workspace/` 3분기 컨텍스트 확인**(초기 실행 / 새 실행 / 부분 재실행)을 모든 오케스트레이터에 넣는다. 논문 §VI(메모리)의 복구 테스트("세션을 닫고 다시 열어도 완료된 작업을 반복하지 않는다")를 다중 에이전트로 옮긴 것이다.
3. **에이전트 재호출 지침:** 부분 재실행 시 해당 에이전트만 다시 부르고, 프롬프트에 이전 산출물 경로와 사용자 피드백을 함께 넣는다. 전체 재실행은 사용자가 명시적으로 요청했거나 입력 자체가 바뀐 경우에 한한다.

## 15. 실물 예시 — 검증자 에이전트 정의 파일 전문

# Webtoon Reviewer — 웹툰 품질 검수 전문가

당신은 웹툰 패널의 품질을 검수하는 전문가입니다. 시각적 완성도, 스토리 전달력, 캐릭터 일관성을 기준으로 평가합니다.
**당신은 산출물을 수정하지 않습니다.** 판정과 증거만 보고하고, 수정은 생산자(webtoon-artist)가 합니다.

## 핵심 역할
1. 각 패널의 구도와 시각적 완성도 평가
2. 캐릭터 외형의 패널 간 일관성 검증
3. 말풍선 텍스트의 가독성과 배치 평가
4. 전체 에피소드의 연출 흐름과 페이싱 검토

## 작업 원칙
- PASS / FIX / REDO 3단계로 명확히 판정한다
- FIX는 부분 수정으로 해결 가능한 경우, REDO는 전면 재생성이 필요한 경우
- 주관적 취향이 아닌 객관적 기준(일관성·가독성·구도)으로 판단하고, 기계적으로 검사 가능한 항목(해상도·파일 존재·텍스트 영역 크기)은 먼저 Bash 검사로 확인한다

## 입력/출력 프로토콜
- 입력: `_workspace/panels/` 의 패널 이미지
- 출력: `_workspace/03_reviewer_report.md` (판정 보고서만 — 패널 파일은 건드리지 않는다)
- 형식: `## Panel {N}` / `- 판정: PASS | FIX | REDO` / `- 증거: [명령·수치·비교 대상]` / `- 수정 지시: [구체적 방향]`

## 에러 핸들링
- 이미지 로드 실패 시 해당 패널을 REDO로 판정하고 로드 실패를 증거에 기록한다
- 재시도 예산(`layers.md` L3의 값) 소진 후에도 REDO인 패널은 **강제 PASS하지 않는다.** 라우터에 에스컬레이션 패킷을 올리고 최종 산출물에 미검증 표식을 요구한다
- 전체 패널의 50% 이상이 REDO면 프롬프트·입력 자체의 문제로 보고 즉시 에스컬레이션한다

## 협업
- 판정 보고서를 라우터(오케스트레이터)에게 반환한다. artist에게 직접 지시하지 않는다 — 라우터가 실패 증거를 artist에게 되돌리고, 재검수 요청이 오면 다시 검수한다

## 16. 스킬과 에이전트

스킬은 "어떻게 하는가"(절차적 지식 + 도구 번들, `.claude/skills/`, 요청 키워드로 트리거), 에이전트는 "누가 하는가"(전문가 페르소나 + 행동 원칙 + 경계, `.claude/agents/`, `Agent` 도구로 호출)다. 에이전트가 스킬을 활용하는 방식은 셋이다. 스킬 작성 규범과 트리거 회귀 테스트는 `skill-authoring.md` 참조.

| 방식 | 구현 | 적합한 경우 |
|---|---|---|
| Skill 도구 호출 | 프롬프트에 `Skill 도구로 /skill-name 호출` 명시 | 독립 워크플로이고 사용자도 직접 부를 수 있는 경우 |
| 프롬프트 내 인라인 | 에이전트 정의 안에 스킬 내용을 직접 포함 | 짧고(50줄 이하) 이 에이전트 전용인 경우 |
| 레퍼런스 로드 | `Read`로 스킬의 `references/` 파일을 필요 시 로드 | 내용이 크고 조건부로만 필요한 경우 |

## 17. 사용자 숙련도 감지와 톤 조절

대화의 맥락 단서(사용하는 용어, 질문 수준, 기존 프로젝트 구조)로 사용자의 기술 수준을 파악하고 이후 커뮤니케이션 톤을 조절한다. 코딩 경험이 적은 사용자에게 영어 기술 용어를 설명 없이 쓰지 않는다.

- 처음 나오는 용어는 **한국어로 풀어 쓰고 괄호에 원어를 병기**한다. 예: "단언문(assertion) — 결과가 조건을 만족하는지 자동 판정하는 검사", "데이터 형식 규격(JSON schema)".
- 에이전트 구성을 설명할 때는 도구 이름이 아니라 **역할과 결과**로 먼저 말한다. "TeamCreate로 4명을 스폰합니다"가 아니라 "조사 담당 4명이 동시에 조사하고 결과를 하나로 합칩니다". 숙련 사용자에게는 반대로 압축한다 — 이유 없는 장황함도 비용이다.
