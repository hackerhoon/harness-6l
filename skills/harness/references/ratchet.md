# 래칫 — 실패를 영구 인프라로 전환하고 하네스를 운영한다

> "에이전트가 실수하는 것을 발견할 때마다, 그 실수를 **다시는 하지 않도록** 하는 해법을 엔지니어링하는 데 시간을 쓴다."

래칫은 되돌아가지 않는 톱니바퀴다. **모든 실패가 시스템을 영구적으로 개선한다.** 프롬프트를 패치하면 대화 하나가 고쳐지고, 하네스를 고치면 이후 모든 실행이 고쳐진다.

## 6단계 엔지니어링 루프

에이전트가 실패하면 이 순서를 따른다. **어떤 단계도 건너뛰지 않는다.**

1. **재현** — 동일한 입력으로 실패를 재현한다
2. **분류** — 근본 원인이 무엇인가: 가이드 누락 / 센서 부재 / 권한 공백 / 상태 소실 / 관찰가능성 사각
3. **계층 선택** — 수정이 속할 가장 강한 계층을 정한다
4. **구현** — 그 계층에 고친다
5. **검증** — 원래 실패한 케이스에서 고쳐졌는지 확인한다
6. **회귀 확인** — 기존 능력이 깨지지 않았는지 확인한다

**1단계를 건너뛰면 유령을 고칠 수 있다.** 재현되지 않는 실패에 대한 수정은 증거가 없는 추측이고, 그 추측이 가이드에 영구히 남는다.
**6단계를 건너뛰면 하나를 고치며 셋을 망가뜨릴 수 있다.**

2단계에서 중요한 것은 **증상이 아니라 실패 클래스**를 식별하는 것이다. "이 파일에서 null 체크를 빠뜨렸다"는 증상이고, "외부 API 응답을 검증 없이 사용한다"가 클래스다. 증상을 고치면 한 번 고쳐지고, 클래스를 고치면 전부 고쳐진다.

## 실패 분류 — 약한 수정과 강한 수정

| 실패 클래스 | 약한 수정 (회피) | 강한 수정 (선호) |
|---|---|---|
| 알려진 나쁜 패턴 | 프롬프트 리마인더 | **린터 규칙(센서)** |
| 컨텍스트 누락 | 더 긴 대화 | **가이드 파일 항목** |
| 잘못된 도구 사용 | 채팅 내 교정 | **권한 경계** |
| 품질 드리프트 | 매 실행 인간 리뷰 | **자동 테스트 스위트** |
| 상태 소실 | 전부 재설명 | **파일 기반 체크포인트** |
| 안전하지 않은 행동 | 재발 안 하길 기대 | **능력 예산 + DENY** |
| 비용 초과 | 수동 모니터링 | **토큰 예산 + 트립와이어** |

## 어느 계층에서 고칠 것인가

**규칙은 "항상 최상단을 고르라"가 아니다.** 사다리 최상단은 환경(권한·스키마·CI)이지만, "컨텍스트 누락"에 CI를 만드는 것은 과잉설계다. 논문이 각 실패 클래스에 **지정한** 강한 수정이 위 표의 오른쪽 열이다.

**진짜 규칙: 위 표 왼쪽 열의 약한 수정 7종을 회피한다.** 약한 수정은 전부 "다음에도 사람이 다시 해야 하는" 것들이라 복리로 쌓이지 않는다.

관찰된 문제에서 시작할 때는 **가장 단순한 계층**부터 본다.

| 문제 | 여기서 시작 | 아직 추가하지 마라 |
|---|---|---|
| 알려진 에러 반복 | 가이드 규칙 | LLM-as-judge |
| 출력 품질 편차 | 계산적 센서 | **다중 에이전트 리뷰** |
| 에이전트 범위 초과 | 권한 경계 | 전체 승인 워크플로 |
| 세션 간 상태 소실 | 체크포인트 | 지식 그래프 |
| 비용 예측 불가 | 토큰·비용 예산 | 동적 가격 책정 |
| 실패가 보이지 않음 | 구조화 로깅 | 전체 관찰가능성 스택 |
| 에이전트 무한 루프 | 재시도 한도 + 타임아웃 | **복잡한 오케스트레이션** |

**에이전트를 실행하기 전에 복잡한 하네스를 만들지 않는다.** 실행하고, 실패를 관찰하고, 실제 증거에서 하네스가 자라게 한다.

### 한 번에 한 계층만

**한 번에 한 계층만 바꾸고, 효과를 측정한다.** 두 계층을 동시에 바꾸면 어느 것이 효과를 냈는지, 어느 것이 회귀를 냈는지 알 수 없다.

## 3회 규칙

인간 리뷰어가 같은 코멘트를 세 번 넘게 쓰면, 그 코멘트는 **구조적 제약이 되어야 한다.**

| 회차 | 조치 |
|---|---|
| 1회 | 가이드 규칙을 추가한다 |
| 2회 | 가이드 규칙이 **실제로 읽히고 있는지** 검증한다 |
| 3회 | 규칙을 위반하는 출력을 **차단하는 센서로 전환**한다 |
| 4회 | **일어나서는 안 된다** |

2회차가 중요하다. 규칙을 추가했는데 또 위반됐다면 규칙이 틀린 게 아니라 **읽히지 않았을** 수 있다 — 파일이 로드되지 않는 위치에 있거나, 다른 규칙과 상충하거나, 너무 길어 묻혔거나.

### 가이드 → 센서 승격 조건

네 가지가 모두 참일 때 옮긴다.

1. 같은 리뷰 코멘트가 3회 넘게 나왔다
2. **주관적 해석 없이** 검사할 수 있다
3. 위반이 실질적 재작업이나 프로덕션 위험을 만든다
4. 검사가 **위반을 어떻게 고치는지까지 설명**할 수 있다

4번이 빠진 센서는 "실패했다"만 말하고 다음 행동을 주지 않아 결국 인간을 부른다.

**승격했으면 가이드에서 그 규칙을 지운다.** 지우지 않으면 가이드가 부풀고, 부푼 가이드는 읽히지 않는다.

## 가이드 가지치기

가이드는 한 줄씩 쌓인다. 가지치기하지 않으면 상충하고, 중복되고, 결국 무시된다. 전형적 실패: 규칙 47("항상 에러 핸들링 추가")을 따르면 규칙 183("함수 20줄 이내")을 위반한다. 몇 달 간격으로 다른 사람이 쓰고 한 번도 조율되지 않았기 때문이다.

**월 1회** 다음을 수행한다.

- 센서가 이미 자동 강제하는 규칙 → **삭제**
- 같은 실패 클래스를 다루는 규칙들 → **통합**
- 상충하는 규칙 쌍 → **조정하고 날짜를 새로 기입**
- 날짜 없는 규칙 → 언제 왜 추가됐는지 확인하고 날짜 부여, 확인 불가면 삭제 후보
- 현행 동작 대비 검증되지 않은 지 오래된 규칙 → 재검증

가이드 파일이 커지면 `.claude/rules/*.md`로 분할하고 `paths:` frontmatter로 스코프를 준다. 그러면 매칭 파일을 읽을 때만 로드되어 규칙 수가 컨텍스트 비용을 늘리지 않는다.

## 롤백

**스코어카드 지표가 하나라도 퇴행하면 롤백한다.** 롤백이 가능하려면 두 가지가 필요하다.

1. 하네스 변경 전 상태로 되돌아갈 수 있어야 한다 — 하네스 파일들이 버전 관리 아래 있고, 변경 전에 커밋이나 태그가 찍혀 있어야 한다
2. 무엇이 퇴행했는지 알 수 있어야 한다 — 변경 전 지표 값이 원장에 남아 있어야 한다

둘 중 하나라도 없으면 "지표가 퇴행하면 롤백한다"는 실행 불가능한 문장이다. **하네스를 크게 바꾸기 전에 되돌아갈 지점을 먼저 만든다.**

## 래칫 원장

`_workspace/harness.md`의 `## 래칫 원장` 섹션에 기록한다. **한 줄이면 충분하다.**

```markdown
## 래칫 원장
| 날짜 | 실패(증상) | 실패 클래스 | 수정 계층 | 무엇을 했나 | 재발 |
|---|---|---|---|---|---|
| 2026-09-02 | 마이그레이션 파일을 검증 없이 수정 | 잘못된 도구 사용 | 권한 | `Edit(/migrations/**)`를 ask로 | 없음 |
| 2026-09-04 | API 응답 shape 불일치를 놓침 | 품질 드리프트 | 센서 | 계약 테스트 추가 | 없음 |
```

**"재발" 열이 이 원장의 핵심이다.** 재발이 기록되면 그 수정은 너무 약한 계층에서 이뤄진 것이다. 한 단계 위로 올린다.

## 성숙 신호

래칫은 선순환을 만든다. 강한 계층에서 고쳐진 실패마다 이후 실행의 총 실패 수가 줄어든다.

초기에는 가이드가 빠르게 자란다 — 흔한 에러들이 처음 발견되기 때문이다. 가장 빈번한 실패 클래스들이 덮이면 증가율이 떨어진다. **성숙한 하네스는 하루 5개가 아니라 주당 1개의 규칙을 추가한다.**

**이 증가율 감소가 하네스가 작동한다는 가장 명확한 신호다.** 반대로 규칙이 계속 빠르게 늘고 있다면, 실패를 너무 약한 계층에서 고치고 있어서 같은 클래스가 다른 얼굴로 계속 돌아오는 것일 수 있다.

## 운영·유지보수

기존 하네스의 점검·수정·동기화 요청("하네스 점검", "감사", "현황", "에이전트/스킬 동기화")은 이 절차를 따른다.

**Step 1 — 현황 감사**
- `.claude/agents/` 파일 목록 ↔ 오케스트레이터가 기술한 에이전트 구성 → 불일치(drift) 목록
- `.claude/skills/` 디렉토리 목록 ↔ 오케스트레이터가 기술한 스킬 구성 → 불일치 목록
- **dangling 검사** — 권한 규칙·hook 명령·체크포인트 참조·가이드가 지시하는 파일이 실재하는가. 존재하지 않는 경로를 가리키는 규칙은 있으나 마나다
- **무효 권한 규칙 검사** — `Write(경로)`/`Glob(경로)`/`MultiEdit(경로)`/`NotebookEdit(경로)` 형태
- **가이드 위생** — 날짜 없는 규칙, 센서가 이미 강제하는 규칙, 상충 쌍
- 감사 결과를 사용자에게 보고한다

**Step 2 — 점진적 추가·수정**
- 에이전트/스킬 추가·수정·삭제를 수행한다
- **변경은 한 번에 하나씩.** 각 변경 후 즉시 Step 3을 실행한다

**Step 3 — 변경 이력 갱신**

```markdown
**변경 이력:**
| 날짜 | 변경 내용 | 대상 | 사유 |
|---|---|---|---|
| 2026-09-02 | 초기 구성 | 전체 | - |
| 2026-09-04 | 검증 에이전트 추가 | agents/verifier.md | 산출물 품질 검증 부족 |
```

이력이 2컬럼이면 4컬럼으로 이관한다. 사유 열이 없으면 나중에 그 변경을 되돌려도 되는지 판단할 수 없다.

**Step 4 — 변경 검증**
- 수정된 에이전트/스킬의 구조 검증
- 트리거에 영향을 주는 변경이면 **트리거 회귀 확인** — 기존 트리거 표현이 전부 살아 있는가 (description은 삭제가 아니라 추가)
- 대규모 변경(아키텍처 변경, 에이전트 3개 이상 추가·삭제)이면 실행 테스트와 드라이런까지
- 파일과 문서의 일치 여부 최종 확인

**settings.json은 이 절차에서도 직접 수정하지 않는다.** 정정할 라인을 제시하고 사용자가 적용한다.

## 진화 트리거

사용자가 "하네스 수정해줘"라고 말할 때만이 아니라, 다음 상황에서도 먼저 진화를 제안한다.

- 같은 유형의 피드백이 **2회 이상** 반복될 때
- 에이전트가 반복적으로 실패하는 패턴이 발견될 때
- **사용자가 오케스트레이터를 우회해 수동으로 작업하는 것이 관찰될 때**

마지막 항목이 가장 중요하고 가장 놓치기 쉽다. 완료율 지표는 **실행된 작업만** 세기 때문에, 사용자가 하네스를 아예 쓰지 않기 시작하면 지표는 오히려 깨끗해 보인다. 하네스가 조용히 버려지는 것은 어떤 스코어카드에도 잡히지 않는다.

### 피드백 반영 경로

| 피드백 유형 | 수정 대상 |
|---|---|
| 결과물 품질 | 해당 에이전트의 스킬 |
| 에이전트 역할 | 에이전트 정의 `.md` |
| 워크플로 순서 | 오케스트레이터 |
| 팀 구성 | 오케스트레이터 + 에이전트 |
| 트리거 누락 | 스킬 description (추가만) |
| 같은 실수 반복 | **가이드 규칙 또는 센서** — 위 3회 규칙을 적용한다 |
| 범위 초과 | **권한 경계** |

매 실행 후 사용자에게 피드백 기회를 준다. 강요하지는 않되 반드시 묻는다 — 피드백이 없으면 래칫이 돌지 않고, 래칫이 돌지 않으면 하네스는 만든 날의 상태로 굳는다.
