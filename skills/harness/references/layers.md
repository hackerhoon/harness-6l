## 통제 신뢰도 사다리

같은 실패를 어느 계층에서 고치느냐가 그 수정이 얼마나 오래 가는지를 결정한다.

| 계층 | 예 | 신뢰도 | 추가 비용 | Claude Code 대응 |
|---|---|---|---|---|
| 메모리 | 대화 중의 이전 교정 | 낮음 | 0 | 세션 종료 시 소실 |
| 프롬프트 | 작업 지시 | 낮음–중간 | 분 | 다음 대화에 없음 |
| 가이드 | 규칙 파일 항목 | 중간 | 분 | `CLAUDE.md`, `.claude/rules/*.md` |
| 센서 | 자동 테스트 | 높음 | 시간 | test/lint를 루프에 배선 |
| **환경** | 권한·스키마·CI | **최고** | 시간–일 | `settings.json`, PreToolUse hook, 서브에이전트 frontmatter, 샌드박스, `-p` 플래그 |

> "프롬프트는 행동을 안내한다. 환경은 실패의 **전체 클래스**를 예방한다."

**중요한 정정:** 사다리 최상단이 항상 정답은 아니다. 회피해야 하는 것은 **약한 수정 8종**(프롬프트 리마인더 / 더 긴 대화 / 채팅 내 교정 / 매 실행 인간 리뷰 / 전부 재설명 / 재발 안 하길 기대 / 수동 모니터링 / 완료 보고를 신뢰)이지, "무조건 최상단을 고르라"가 아니다. 실패 클래스마다 **지정된** 강한 수정이 있다(`ratchet.md`의 실패 분류표). "컨텍스트 누락"에 CI를 만드는 것은 과잉설계다.

## L1 가이드 — 피드포워드

실행 **전에** 읽혀 알려진 실패를 예방한다.

### 본체는 `CLAUDE.md`다

Claude Code는 `CLAUDE.md`를 읽고 `AGENTS.md`는 읽지 않는다. 다른 도구와 규칙을 공유해야 하면 `CLAUDE.md` 안에 `@AGENTS.md` 한 줄을 넣거나 심볼릭 링크를 건다. **`AGENTS.md`를 만들고 거기에 build/test/lint를 적으면 그 내용은 세션에 들어오지 않는다.**

로드 순서(넓은 것 → 좁은 것): managed policy → `~/.claude/CLAUDE.md` → `./CLAUDE.md` 또는 `./.claude/CLAUDE.md` → `./CLAUDE.local.md`. 상위 디렉토리 파일은 시작 시 로드되고, **하위 디렉토리 파일은 그 디렉토리의 파일을 읽을 때 지연 로드**된다.

`@path` import는 상대·절대 모두 가능하고 상대는 import를 담은 파일 기준이며 최대 4 hop이다. **import는 컨텍스트를 줄이지 않는다** — 시작 시 전부 로드된다.

### 최소 가이드 구성

```markdown
# {프로젝트명}

LANGUAGE: {주 언어}
BUILD: {정확한 빌드 명령}
TEST:  {정확한 테스트 명령}
LINT:  {정확한 린트 명령}

## 규칙
- (2026-09-02) /config는 물어보지 않고 수정하지 않는다
- (2026-09-02) 코드 변경 후에는 매번 TEST 명령을 실행한다

## 안티패턴
- (2026-09-02) {관찰된 구체적 실패}. 증상: {…}. 대신: {…}
```

**모든 항목에 날짜를 단다.** 날짜 없는 200줄 가이드는 하네스가 아니라 기술 부채다. 날짜가 있어야 언제 왜 추가됐는지 추적하고, 낡은 규칙을 가지치기할 수 있다.

### 실행 가능한 동작과 관찰 가능한 기준만 쓴다

동기부여성 문구는 가이드가 아니다.

| 쓰지 마라 | 대신 |
|---|---|
| "철저히 조사하라" | 명명된 출처 목록 + 정지 규칙 + 인용 요건 |
| "좋은 코드를 써라" | 린트 명령 + 테스트 명령 + 구체적 패턴 이름 |
| "신중하게 처리하라" | 어떤 조건에서 무엇을 하고, 무엇을 하면 안 되는가 |

### 권위 역전 — 이것이 없으면 가이드는 대화와 같다

> **가이드와 대화가 충돌하면 가이드가 이긴다.**

파일에 대화보다 높은 권위를 주는 이 역전이 하네스를 지속시킨다. 가이드 파일은 시스템의 기록(system of record)이지 제안이 아니다. 이 문장을 산출하는 `CLAUDE.md`에 실제로 써 넣는다.

**단, `CLAUDE.md`는 강제되지 않는다** — 문서 표현으로 "context, not enforced configuration"이다. 반드시 실행돼야 하는 규칙(예: 푸시 전 테스트)은 가이드가 아니라 **hook**으로 쓴다.

### 가이드 위생 — 규칙은 썩는다

규칙 47("항상 에러 핸들링 추가")을 따르면 규칙 183("함수 20줄 이내")을 위반한다. 몇 달 간격으로 다른 사람이 쓰고 한 번도 조율된 적이 없기 때문이다. 월 1회 다음 5문항으로 점검한다.

1. 에이전트가 각 규칙을 **주관적 판단 없이** 검증할 수 있는가?
2. 모든 규칙이 **관찰된 실패**로 추적되는가?
3. **상충하는 규칙 쌍**이 있는가?
4. 린터나 테스트(센서)로 **대체 가능한** 규칙이 있는가? 있으면 규칙을 지우고 센서로 옮긴다
5. 각 규칙이 마지막으로 **현행 동작 대비 검증된 때**는 언제인가?

### 규칙이 커지면 `.claude/rules/*.md`로 분할한다

규칙 파일에 `paths:` frontmatter를 주면 **매칭되는 파일을 읽을 때만 로드**된다. 이것이 "규칙 수 증가 = 컨텍스트 비용 증가"를 끊는 유일한 네이티브 수단이다. `@import`로는 안 된다(전량 로드).

### 가이드가 없을 때의 비용

매 세션이 0에서 시작한다. 에이전트는 빌드 시스템·코딩 패턴·금지된 연산·프로젝트 구조를 코드베이스만 보고 추론해야 한다. 지난주에 고친 실수를 반복하고, 지난달에 금지한 패턴을 쓰고, 읽기 전용이어야 할 파일을 수정한다. **대화 중의 모든 교정은 세션이 끝나면 사라진다.** 가이드 파일이 교정을 영구화한다.

### 왜 여기에 시간을 쓰는가 — 복리 (논문 §XIV(대안 비교).A)

**프롬프트 교정은 복리되지 않는다 — 매 대화에서 다시 적용해야 한다.** 반면 오늘 추가한 가이드 규칙 하나는 이후 **모든** 실행에서 같은 오류 클래스를 막고, 센서 하나는 모든 출력에서 같은 결함 클래스를 잡고, 권한 경계 하나는 모든 세션에서 같은 사고 클래스를 막는다. 하네스 개선이 빠르게 복리되는 이유는 그것이 대화가 아니라 **구조**이기 때문이다.

## L2 센서 — 피드백

실행 **후에** 출력을 검증한다. 가이드가 막지 못한 것을 잡는다.

| 유형 | 예 | 속도 | 비용 | 결정성 |
|---|---|---|---|---|
| **계산적** | 린터, 타입체커, 유닛 테스트, 스키마 검증 | 빠름 | 무료 | 결정적 |
| **추론적** | LLM 심판, AI 코드리뷰 | 느림 | 비쌈 | 비결정적 |

### 계산적 센서 우선 — 정량 근거

린터 규칙 1개는 무료로 돌면서 리뷰 코멘트 한 클래스를 영구 제거한다. API 응답 구조를 검증하는 테스트는 밀리초가 들고 깨진 통합을 막는다. "코드 품질"을 평가하는 LLM 심판은 토큰을 쓰고 비결정적 판정을 낸다. **$10/run짜리 심판을 하루 50회 도는 작업에 붙이면 하루 $500이다.** 같은 클래스를 잡는 린터는 무료다.

**결정적 규칙으로 표현할 수 없는 검사에만 추론적 센서를 추가한다** — 고객 이메일의 어조, 법률 요약의 정확성, 설계 결정의 품질 같은 것.

### 추론적 센서는 게이트가 아니라 자문 신호다

LLM 판정을 통과/차단 게이트로 쓰면 비용과 비결정성이 파이프라인에 박힌다. 판정을 **로깅**하고, 인간 리뷰와의 **일치율을 측정**하고, 패턴이 충분히 명확해지면 **결정적 검사로 대체**한다.

### 자기검증 패턴 — 가장 강한 하네스 패턴 (`verified_step` 정본)

에이전트에게 자기 센서에 대한 접근권을 준다. 각 단계 후 사전 정의된 검사를 실행하고 실패를 **에러 텍스트와 함께** 되먹인다. 이것은 모델이 자기 품질을 판단하는 것이 아니라, **외부의 결정적 검사를 실행하고 그 결과에 반응**하는 것이다.

```
verified_step(agent, task, sensors):
    result = agent.execute(task)
    for sensor in sensors:
        verdict = sensor.check(result)          # 종료코드
        if not verdict.passed:
            result = agent.fix(result, verdict) # 에러 텍스트를 그대로 넘긴다
            if not sensor.check(result).passed:
                return escalate(task, verdict)  # 두 번 실패하면 올린다
    return result
```

에이전트 정의에 이 루프를 문자로 기술한다. "테스트를 실행하라"가 아니라 "**변경 후 TEST 명령을 실행하고, 실패하면 에러 텍스트를 그대로 읽고 수정하고, 한 번 더 실패하면 에스컬레이션한다**"라고 쓴다.

**수정은 1회다.** `verified_step`은 검증 → 실패 → 수정 1회 → 재검증이고, 그 재검증이 실패하면 에스컬레이션한다. 즉 "2회 실패 시 에스컬레이션"이지 "2회 재시도"가 아니다. 이 의사코드의 사본을 다른 파일에 만들지 않는다 — 여기를 가리킨다. 바깥 루프(`agentic_loop`)와의 관계는 L3.

### 점진적 구축 — 있는 것부터 배선한다

프로젝트의 테스트 스위트·린터·타입체커가 이미 센서다. 새로 만들기 전에 이것들을 에이전트 실행 루프에 배선한다. 실사용에서 관측된 실패 패턴: 검증 스크립트가 **존재하는데 루프에 배선되지 않아 한 번도 실행되지 않는 것**. 센서는 존재만으로는 아무것도 하지 않는다.

### 센서 커버리지 테스트 — 무인 운영 전 필수 (정본)

**5문항 전체가 "예 = 이 조건이 충족됐다" 극성이다.** 한 문항이라도 극성이 뒤집히면 집계 규칙이 반대로 작동해, 가장 센서가 필요한 상태를 "충족"으로 통과시킨다.

1. 인간 검사 없이 에이전트가 **자기 출력을 검사**할 수 있는가?
2. 모든 중요 출력에 **계산적 센서가 최소 1개** 있는가?
3. 센서 결과가 **추세 분석용으로 기록**되는가?
4. 에이전트 동작이 변해도 **센서는 안정적**인가?
5. 어떤 센서도 건드리지 않고 **조용한 회귀가 사용자에게 도달할 수 없는가**?

하나라도 아니오면 무인 운영을 켜기 전에 그 센서를 추가한다.

5번이 가장 자주 뒤집힌다. "…도달할 수 **있는가**"로 쓰면 예=결함이 되어 나머지 넷과 극성이 어긋난다. **이 5문항의 사본을 만들지 않는다** — 답을 적어 두는 기록란은 `assets/workspace-harness.template.md`의 산출물 섹션이고, 다른 파일은 이 절을 가리킨다.

### 적대적 센서 — 100% 통과는 의심스럽다

매 실행 100% 통과하는 테스트 스위트는 좋은 신호가 아니다. 테스트가 너무 쉽거나, 에이전트가 문제를 실제로 풀지 않고 **테스트를 통과하는 출력을 만드는 법을 배운** 것이다. 필요한 것: 맞아 보이지만 숨은 위반이 있는 입력, 스키마 검증은 통과하지만 데이터가 틀린 출력, 빌드되고 린트를 통과하지만 로직이 틀린 코드.

**센서 스위트는 좋은 포맷을 확인하는 것이 아니라 나쁜 작업을 거부해야 한다.** 상세는 `skill-authoring.md`.

## L3 에이전틱 루프

단일 모델 호출이 아니다. **유한한 사이클**이다: 계획 → 도구로 실행 → 센서로 검증 → 수정 → 전진 또는 에스컬레이션. 모든 단계가 관찰 가능하고 모든 재시도가 카운트된다.

### 원문 루프 — `agentic_loop` (논문 §V(에이전틱 루프))

L2의 `verified_step`이 **한 단계 안**의 검증이라면 `agentic_loop`은 **계획 전체**를 도는 바깥 루프다. 둘은 경쟁하지 않고 중첩된다 — 바깥은 단계를 넘기고, 안쪽은 한 단계를 통과시킨다.

```
agentic_loop(task, agent, sensors, budget):
    plan = agent.plan(task)
    for step in plan.steps:                        # 단계 단위 루프
        for attempt in range(budget.max_retries):  # 단계당 재시도 예산
            result  = agent.execute(step)
            verdict = verify(result, sensors)
            if verdict.passed: break
            if not verdict.retryable:              # ← 여기가 가장 자주 소실된다
                return escalate(step, verdict)
        else:                                      # 예산 소진
            return escalate(step, "budget exhausted")
    return synthesize(plan.results)
```

**규범: 재시도해도 결과가 달라지지 않는 실패(권한 거부·인증 없음·입력 스키마 오류·비가역 차단)는 예산을 소모하지 않고 즉시 에스컬레이션한다.** 재시도 예산은 *일시적* 실패(플레이키 테스트, 타임아웃, 경합, 부분 출력)를 위한 것이다. 재시도 불가 실패에 예산을 태우면 두 가지를 함께 잃는다 — 시간과, 인간이 개입할 수 있었던 가장 이른 시점. `retryable` 여부를 판별할 수 없으면 재시도 불가로 취급한다(안전한 쪽이 에스컬레이션이다).

**예산 소진 경로도 정지가 아니라 에스컬레이션이다.** `for ... else`는 `escalate(step, "budget exhausted")`로 빠진다. 정지는 사유를 남기지 않고 에스컬레이션은 남긴다 — 아래 5요소 패킷을 그대로 붙인다.

**재시도 횟수가 두 개인 이유.** Table IV 기본값은 **단계당 3회**다. 논문 §X(빌드 경로).B의 초기 배선은 **1회 재시도·2회 실패 시 에스컬레이션**이다. **이 스킬은 초기 배선 값(1회 재시도)으로 시작하고 래칫으로 조정한다** — 관측 근거 없이 3회로 시작하면 실패 하나의 비용이 세 배가 되고, 그 비용이 어디서 났는지 알 수 없다. 다른 파일의 재시도 서술은 이 문단을 따른다.

### 루프 경계 6종 — 강제성을 함께 적는다 (`enforced_by` 정본)

| 경계 | 기본값 | Claude Code 강제 수단 | `enforced_by` |
|---|---|---|---|
| 단계당 최대 재시도 | 3회 (이 스킬 초기 배선 1회) | 서브에이전트 frontmatter `maxTurns` | `subagent` |
| 최대 소요시간 | 30분/task | `PostToolBatch` hook `exit 2` | `hook` |
| 최대 토큰 | 100K/task | 네이티브 없음. transcript 스트리밍 합산 후 hook | `hook` (정의는 아래) |
| 최대 비용 | $5/task | 대화형에 등가 설정 **없음**. `claude -p --max-budget-usd 5`에서만 | 대화형 `none` / `-p-flag` |
| 최대 도구 호출 | 50회/task | PreToolUse / `PostToolBatch` hook 카운터 | `hook` |
| 정지 조건 | 항상 정의 | 설계 사항 | — |

**`hook` 표기는 조건부다.** hook은 스크립트를 설치하는 것만으로 발화하지 않고 **사용자가 `settings.json`의 `hooks` 블록에 등록한 뒤에야** 발화한다. 따라서 **하네스 구축을 막 끝낸 시점의 hook 예산은 언제나 `none`**이고, 사용자가 등록을 확인해 준 뒤에 `hook`으로 올린다. 절차와 등록 JSON은 `enforcement.md`.

**토큰 예산의 정의 — 이것이 아니면 숫자가 폭주한다.** `hook`이 세는 토큰은 **유니크 `requestId` 기준 `input_tokens + output_tokens`의 합 — 새로 처리된 입력 + 생성된 출력**이다. 캐시 필드는 둘 다 제외한다: `cache_read`는 턴마다 컨텍스트 전체가 재계상돼 폭주하고, `cache_creation`은 캐시 만료 시 컨텍스트 전체가 한 요청에 잡혀 단일 요청이 예산을 터뜨린다. 이것은 **작업량 근사치이지 청구액도 컨텍스트 크기도 아니다.** 작업 시작 시점을 기준선으로 잡고 그 증가분만 센다. `cache_read`를 턴마다 재합산하거나 중복 레코드를 이중 계상하면 100K 예산이 세 번째 턴에 소진된다(실측). 상세는 `enforcement.md`「hook 보안·한계」.

**모든 예산의 단위는 per-task다.** 여기서 작업(task)은 **사용자 프롬프트 1턴**이며, 카운터는 `${session_id}-${prompt_id}` 키로 분리되어 다음 프롬프트에서 자연 리셋된다. 세션 단위 누적이 아니다.

**어떤 예산이든 소진되면 루프는 다음 4가지를 반환한다:** 현재 최선의 산출물 / 완료된 작업 / 미해결 이슈 / **정지 사유**. 부분 실패를 유창한 최종 답변 뒤에 숨기지 않는다. 실사용에서 이 규범이 깨지는 전형적 형태는 "완료했습니다"라고 보고하면서 검증 단계가 한 번도 돌지 않은 경우다.

### 에스컬레이션은 실패가 아니다

올바르게 에스컬레이션하는 에이전트가 자신만만한 오답을 내는 에이전트보다 **가치 있다.** 에스컬레이션 패킷은 다음 5요소를 담는다.

```markdown
## 에스컬레이션
- **필요한 결정:** {인간이 내려야 할 결정 한 문장}
- **권장안:** {내가 권하는 선택과 이유}
- **이미 시도한 대안:** {무엇을 해봤고 왜 안 됐는가}
- **대기 비용:** {지금 멈추면 무엇이 늦어지는가}
- **무응답 시 기본 조치:** {응답이 없으면 취할 가장 안전한 행동}
```

마지막 항목이 없으면 에스컬레이션은 그냥 정지다.

### 배경 에이전트 규칙

루프는 정상 실행 중에 인간의 주의를 요구해서는 안 된다. 인간은 의도를 제공하고, 결과를 검토하고, 에스컬레이션을 처리한다. 그 사이는 전부 하네스가 처리한다.

> 팀·오케스트레이터·핸드오프 설계는 `multi-agent.md`. 다만 그 파일을 열기 전에, 출력 품질 편차는 **계산적 센서**로, 무한 루프는 **재시도 한도 + 타임아웃**으로 먼저 다뤄본다. 다중 에이전트 리뷰와 복잡한 오케스트레이션은 더 단순한 계층이 자리 잡은 뒤에 추가한다.

## L4 메모리와 상태

모든 모델 호출은 빈 컨텍스트에서 시작한다. **모델에는 지속 기억이 없다. 하네스가 연속성을 제공한다.**

| 계층 | 지속 범위 | 재시작 생존 | 구현 |
|---|---|---|---|
| 컨텍스트 윈도우 | 현재 턴 | 아니오 | 대화 버퍼 |
| 스크래치패드 | 현재 작업 | 아니오 | `_workspace/` 작업 파일 |
| 아티팩트 스토어 | 세션 간 | 예 | `_workspace/`, git |
| 결정 로그 | 세션 간 | 예 | `harness.md`의 래칫 원장 |

### 파일이 메모리다

가장 단순한 지속 메모리는 파일시스템이다. 대부분의 에이전트 워크플로에서 벡터 DB보다 싸고 단순하고 신뢰성이 높다. 에이전트는 세션 시작 시 이 파일들을 읽고, 의미 있는 단계마다 갱신한다.

L4는 6계층 중 **Claude Code에서 플랫폼 마찰이 전혀 없는 유일한 계층**이다. `_workspace/`는 protected path가 아니며 어떤 제약도 받지 않는다.

### 체크포인트 — 활성 작업당 최신 1개

```markdown
## 체크포인트
- **task_id:** {식별자}
- **status:** in_progress | blocked | done
- **완료된 단계:** {목록}
- **산출물:** {파일 경로 목록}
- **다음 단계:** {구체적으로}
- **갱신:** {ISO 날짜}
```

**덮어쓰기가 곧 만료다.** 3주 전 체크포인트는 없어진 파일, 번복된 결정, 대체된 아티팩트를 참조한다. 에이전트가 그것을 읽고 낡은 상태로 판단한다. 활성 작업당 최신 1개만 유지하면 이 실패 클래스가 구조적으로 사라진다. (산출물 아티팩트 자체는 보존한다 — 만료 대상은 체크포인트다.)

### 복구 테스트

다단계 작업 중간에 세션을 닫고 다시 연다. 에이전트는 체크포인트를 읽고, 마지막 완료 단계를 식별하고, **다음 단계부터 재개**해야 한다 — 완료된 작업을 반복하지 않고, 인간에게 작업을 다시 설명해달라고 하지 않고. 못 하면 메모리 계층이 불충분한 것이다.

### 컴팩션의 소유권

장기 실행 시 컨텍스트가 찬다. 오래된 컨텍스트를 요약하고, 최근 행동과 결정을 보존하고, 워킹셋을 예산 안에 유지한다. 압축 자체는 모델 호출이지만 **언제 무엇을 압축할지의 결정은 에이전트가 아니라 하네스에 속한다.**

압축된 컨텍스트에 **부정 예시**(이런 경우는 이 경로가 아니다)를 추가하면 라우팅 정확도가 **73% → 85%**로 오른다는 결과가 보고돼 있다. 이것은 스킬 description과 near-miss 트리거 설계에 직접 적용된다 — `skill-authoring.md` 참조.

### 메모리와 가이드는 다르다

메모리는 **무슨 일이 있었는지** 기록하고, 가이드는 **무엇이 일어나야 하는지** 정의한다. 모든 향후 실행에 중요한 규칙을 옛 대화의 기억에 의존하지 않는다.

- **가이드로 승격:** 안정적인 선호, 정책, 절차
- **메모리에 남김:** 일시적 사실, 작업별 논의, 탐색적 추론

## L5 권한과 예산

**모델은 자기를 제한할 수 없다.** 접근 가능한 도구는 다 쓰고, 닿는 파일은 다 쓰고, 작성 가능한 메시지는 다 보낸다. 권한은 모델의 속성이 아니라 **하네스의 속성**이다. 하네스가 1차 보안 경계다.

L5는 6계층 중 **Claude Code에서 완전히 강제되는 유일한 계층**이다.

### 기본 행동 정책

| 행동 | 기본 | 이유 |
|---|---|---|
| 소스 파일 읽기 | 허용 | 가역적 관찰 |
| 프로젝트 파일 쓰기 | 허용 + 기록 | git으로 복구 가능 |
| 테스트·린터 실행 | 허용 | 부작용 없음 |
| 원격 푸시 | 질문 | 외부 가시성 |
| 프로덕션 배포 | **인간 전용** | 되돌리기 어려움 |
| 외부 메시지 발송 | 질문 | 평판 영향 |
| 데이터·파일 삭제 | **인간 전용** | 잠재적 비가역 |

### 4가지 예산 차원 — 첫 무인 실행 전에 전부 정한다

- **Scope** — 어떤 계정·도구·파일·연산이 가용한가
- **Rate** — 구간당 최대 쓰기·커밋·외부 호출
- **Reversibility** — 안전하게 롤백 가능한가. 비가역 행동은 인간 승인 필수
- **Visibility** — **누가 통보받고 어떤 증거가 감사용으로 보존되는가**

Visibility가 빠지면 "모든 중요한 출력을 추적할 수 있다"는 명제가 거짓이 된다. 네 번째 차원을 잊지 않는다.

### 원장은 증거이자 공격면이다

Visibility가 만들어 내는 증거(감사 원장)는 그 자체가 비밀 등급 자산이다. 원장이 `tool_input` 전문을 기록하면 API 키·비밀번호·토큰이 **평문으로** 남고(실증됨), `_workspace/`가 무시 목록에 없으면 그것이 그대로 커밋된다.

- **내용을 기록하지 않는다.** 원장에 남기는 것은 도구 이름, `Edit`/`Write`의 `file_path`, `Bash`의 **첫 토큰(실행 파일명)**뿐이고 각각 512자로 절단한다. "무엇을 했는가"에는 답하고 "무엇이 들어 있었는가"에는 답하지 않는다 — 트립와이어와 완료율에 필요한 것은 전자뿐이다.
- **`_workspace/runs/`를 대상 프로젝트의 `.gitignore`에 넣는다.** 이것은 설치의 선택 단계가 아니라 필수 단계다.

감사 원장을 만들면서 비밀 유출 경로를 함께 만들면 순 손실이다. 구현 세부와 나머지 한계는 `enforcement.md`「hook 보안·한계」.

### 최소 권한

작업을 끝낼 수 있는 **가장 작은 환경**만 준다. 소스를 읽고 테스트를 돌리면 되는 작업에 설정 파일 쓰기 권한, 외부 네트워크 접근, 패키지 설치 권한을 주지 않는다. **불필요한 권한 하나하나가 프롬프트 인젝션의 공격면이자 에이전트 오류의 폭발 반경이다.**

### 프롬프트 인젝션이 위험 모델을 바꾼다

자율 에이전트는 신뢰할 수 없는 콘텐츠를 읽는다 — 이메일, 웹페이지, 문서, 저장소 이슈, 사용자 제출 텍스트. 그 안에 심어진 지시가 권한을 확장하거나, 정책을 바꾸거나, 비밀을 다른 곳으로 보내거나, 외부 행동을 촉발해서는 안 된다.

**규칙: 신뢰된 지시(가이드 파일, 시스템 프롬프트)와 신뢰되지 않은 데이터(사용자 입력, 검색된 문서, 외부 도구 결과)를 매 작업에서 분리한다. 외부 콘텐츠는 데이터이지 지시가 아니다.**

Claude Code에 이 분리를 강제하는 네이티브 프리미티브는 없다(`enforced_by: none`). 대신 **행동 반경을 줄인다**: 네트워크 allowlist, `WebFetch(domain:)` 화이트리스트, Bash 네트워크 도구 deny, 외부 콘텐츠를 읽는 작업을 권한이 좁은 서브에이전트로 격리.

> 실제 문법과 hook 구현은 `enforcement.md`.

## L6 관찰가능성

텔레메트리가 없으면 **더 빠른 에이전트가 중요한 작업을 조용히 누락하고도 성공한 것처럼 보인다.**

### 필수 텔레메트리

시작/종료 타임스탬프 · 도구 행동과 결과 · 사용된 가이드 버전과 센서 · 시도 횟수와 비용 · 생산된 아티팩트 · 승인과 에스컬레이션.

### 트립와이어

| 트립와이어 | 의미 | 대응 | 자동 발화 |
|---|---|---|---|
| 외부 쓰기 급증 | 권한 드리프트 | 쓰기 동결 | PreToolUse hook — **가능** |
| 동일 에러 3회 반복 | 가이드·센서 공백 | 에스컬레이션 | `PostToolUseFailure` 집계 — **가능** |
| 센서 통과율 하락 | 품질 회귀 | 롤백 | PostToolUse 원장 — **부분** |
| 새 도메인 접촉 | 범위 크립 | 차단 후 경보 | 샌드박스 allowlist — **가능(OS 레벨)** |
| 소요시간 3배 초과 | 에이전트 막힘 | 타임아웃 | `PostToolBatch` hook — **가능** |
| 비용 평균 2배 초과 | 폭주 루프 | 일시정지 후 조사 | **대화형에서는 토큰 프록시로만 근사** |

여섯 중 **넷**은 hook·샌드박스로 자동 발화와 차단이 가능하다. 나머지 둘은 정직하게 낮춰 적는다.

- **센서 통과율 하락 — 부분.** 원장은 도구의 성공/실패만 남기고 "센서 실행"과 "일반 도구 호출"을 구별하지 않는다. 즉 이 신호는 **도구 실패율의 프록시일 뿐 센서 판정을 구분하지 못한다.** 진짜 통과율이 필요하면 TEST/LINT 명령의 종료코드를 별도로 기록해야 한다(`harness.md`의 "최근 센서 관측" 행).
- **비용 평균 2배 초과 — 근사.** transcript에 비용 필드가 없으므로 대화형에서는 토큰 프록시까지만 가능하다.

### 관찰가능성은 디버깅 인프라다

잘못된 결과가 나왔을 때 첫 질문은 "어디서 틀렸는가"다. 구조화된 로그가 없으면 답을 찾는 데 대화 전체를 재생해야 한다. 로그가 있으면 예상 밖 데이터를 반환한 도구 호출, 실패했어야 하는데 통과한 센서, 가이드 규칙을 무시한 단계를 정확히 짚을 수 있다. 오버헤드가 아니다.

### 비용 귀속은 일별이 아니라 작업별로

하루 $50은 100개를 완료했는지 2개인지 모르면 무의미하다. **검증된 결과당 비용**이 하네스가 개선되는지를 드러내는 지표다. 새 가이드 규칙이 재시도를 3회에서 1회로 줄이면 작업당 비용이 60% 내려간다.

### 운영 리뷰 질문 5개

1. 이번 주 가장 비싼 작업 유형은?
2. 가장 많은 에러를 잡은 센서는?
3. 가장 많이 위반된 가이드 규칙은?
4. 완료된 작업을 처음부터 끝까지 추적할 수 있는가?
5. 에이전트가 실패하기 시작하면 **1시간 안에** 알 수 있는가?

답할 수 없는 질문이 있으면 그 항목의 계측이 빠진 것이다.

### 지표별 계측 소스 — 소스가 없는 지표는 적지 않는다

진짜 지표는 하나다: **수동 개입 없이 완료되고 수용 가능한 증거를 낸 작업 수.** 나머지는 계측 소스가 실제로 있을 때만 추가한다 — 계측할 수 없는 지표를 문서에 적어두는 것이 바로 "안전으로 위장한" 상태다.

| 지표 | 계측 소스 | 판정 |
|---|---|---|
| 에스컬레이션률 | `Notification`/`PermissionRequest` hook, OTel `tool_decision` | **네이티브 있음** |
| 권한 경계가 1회 차단 | `PermissionDenied` hook 원장 | **hook 등록 필요** — 차단된 호출은 `PostToolUse`도 `PostToolUseFailure`도 발화시키지 않는다 |
| 가이드 증가율 (감소해야 정상) | `CLAUDE.md`/`.claude/rules/` git 히스토리 | **네이티브 있음** |
| 재작업률 | OTel `code_edit_tool.decision` | **OTel 필요** |
| 작업당 비용 | `-p --output-format json`의 `total_cost_usd` 또는 OTel | **대화형 transcript에 cost 필드 없음** |
| 완료율 / 복구시간 | `harness_report.sh` — `<sid>.tasks.jsonl`의 `task_end` (hook 등록 후) | **네이티브 소스 없음.** 하네스가 원장을 써야만 존재한다 — 지표가 아니라 산출물 요구사항으로 다룬다 |

위 다섯 줄은 소스를 켜거나 등록하면 얻을 수 있고, 마지막 줄은 하네스가 직접 만들어야 존재한다. 원장을 만들 때의 기록 규범은 L5「원장은 증거이자 공격면이다」, 데이터 소스의 실제 경로는 `enforcement.md`「관찰가능성 데이터 소스」.

## 계층 간 이동 규칙

수정은 한 계층에 머물지 않는다. 시간이 지나면 더 강한 계층으로 옮겨간다.

| 이동 | 조건 |
|---|---|
| 메모리 → 가이드 | 그 교정이 **모든 향후 실행**에 적용돼야 할 때 |
| 가이드 → 센서 | 같은 리뷰 코멘트가 3회 넘게 나올 때 / 주관적 해석 없이 검사 가능할 때 / 위반이 실질적 재작업이나 프로덕션 위험을 만들 때 / 검사가 **복구 방법까지 설명**할 수 있을 때 |
| 센서 → 환경 | 검사를 우회할 수 있고, 우회가 실제로 발생할 때 |
| 가이드 삭제 | 센서나 환경이 그 규칙을 이미 자동 강제할 때 |

마지막 줄이 중요하다. **센서로 옮긴 규칙은 가이드에서 지운다.** 지우지 않으면 가이드가 부풀고, 부푼 가이드는 결국 읽히지 않는다.

> 실패를 어느 계층에서 고칠지 결정하는 절차는 `ratchet.md`.
