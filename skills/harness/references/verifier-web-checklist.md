# 웹 경계면 체크리스트 (Next.js / React)

**`verifier-agent.md`의 스택 특화 부록이다. 먼저 `verifier-agent.md`를 읽어라** — 검증자 독립 규범(쓰기 권한 없음), 실패 보고 6필드, 계산적/추론적 승격 규칙은 전부 그쪽에 있고 여기서 반복하지 않는다.

이 파일은 **웹 프로젝트일 때만** 읽는다. 판별은 한 줄이다 — `package.json`에 `next` 또는 `react`가 있고 `src/app/` 또는 `pages/`가 존재하는가. 아니면 이 파일을 닫고 `verifier-agent.md` 8절의 범용 체크리스트를 그 스택 어휘로 인스턴스화하라. 웹이 아닌 프로젝트에 아래 항목을 들이대면 25개 중 20개가 "해당 없음"이 되고, **해당 없음이 대부분인 체크리스트는 검증자에게 "대충 넘어가도 된다"를 학습시킨다.**

여기 있는 것은 전부 `verifier-agent.md` 3-3의 **추출 → 정규화 → 대조** 3단계를 Next.js 어휘로 인스턴스화한 것이다. 새로운 방법론은 없다.

## 1. 경계면 4종의 결정적 검사 절차

양쪽을 **동시에 열어** 대조한다. 한쪽만 읽으면 이 클래스는 원리적으로 안 잡힌다. 명령은 `ripgrep`(`rg`) 기준이며, 없으면 `grep -rn`으로 대체한다.

```
(A) API 응답 ↔ 프론트 훅 타입
  rg -n "NextResponse.json\(" src/app/api/ → shape 추출  |  rg -n "fetchJson<" src/hooks/ → 제네릭 T 추출
  → 엔드포인트별 shape ↔ T 1:1 대조. 래핑 확인({ data: [...] }면 훅이 .data를 꺼내는가)
    주의: 페이지네이션({items,total,page}) vs 배열 기대 / snake_case DB → camelCase API → 프론트 타입 / 202 즉시 응답 vs 최종 결과

(B) 파일 경로 ↔ 링크·라우터 경로
  src/app/ 하위 page.tsx 경로 → URL 패턴 생성 ((group) 제거, [param]은 동적 세그먼트)
  rg -nE "href=|router\.push\(|redirect\(" src/ → 링크 값 수집
  → 각 링크가 URL 집합에 존재하는가 대조. route group 접두사(dashboard/ 등) 누락 주의

(C) 상태 전이 맵 ↔ 실제 업데이트 코드
  STATE_TRANSITIONS 맵 → 허용 전이 목록  |  rg -n "status:" src/app/api/ → .update({ status }) 수집
  → 코드에 있고 맵에 없음 = 무단 전이 / 맵에 있고 코드에 없음 = 죽은 전이. 특히 중간 → 최종 상태 전환 누락

(D) API 엔드포인트 ↔ 프론트 훅 1:1 매핑
  route.ts의 HTTP 메서드별 엔드포인트 목록 ↔ use*.ts의 fetch URL 목록
  → 훅이 호출하지 않는 엔드포인트 = "사용 안 됨". 의도적(관리 API)인지 호출 누락인지 판정만 사람 몫, 목록 생성은 결정적
```

**정규화 규칙을 보고서에 적어라.** (B)에서 route group을 어떻게 제거했는지, (A)에서 케이스 변환을 어느 방향으로 맞췄는지를 적지 않으면 다음 검증자가 같은 대조를 재현할 수 없고, 재현 불가능한 검사는 센서가 아니다.

**이 네 절차가 3회 이상 값을 내면 스크립트로 굳혀 CI에 건다.** 에이전트가 매번 판단으로 수행하는 동안은 과도기다(`verifier-agent.md` 1절).

## 2. 웹 경계면 체크리스트 25항목

경계면 25항목 + 적대적 검사 2항목. 검증자 정의에 그대로 붙여 쓴다. 각 항목은 1절의 절차 또는 단일 `rg` 한 줄로 검사 가능하다 — **주관적 판단을 요구하는 항목은 하나도 없다.**

```markdown
#### API ↔ 프론트엔드 연결
- [ ] 모든 API route의 응답 shape과 대응 훅의 제네릭 타입이 일치
- [ ] 래핑된 응답({ items: [...] })을 훅에서 unwrap하는지 확인
- [ ] snake_case ↔ camelCase 변환이 일관되게 적용
- [ ] 즉시 응답(202)과 최종 결과의 shape이 프론트에서 구분되는지 확인
- [ ] 모든 API 엔드포인트에 대응하는 프론트 훅이 존재하고 실제로 호출됨
- [ ] API 에러 응답 형태({ error })가 프론트 에러 처리 분기와 일치 — 성공 형태만 맞추고 실패 형태가 어긋나는 경우
#### 라우팅 정합성
- [ ] 코드 내 모든 href/router.push 값이 실제 page 파일 경로와 매칭
- [ ] route group ((group))이 URL에서 제거되는 것을 고려한 경로 검증
- [ ] 동적 세그먼트([id])가 올바른 파라미터로 채워지는지 확인
- [ ] 폴더의 동적 세그먼트 이름([id]/[slug])과 코드의 params 접근 키가 일치
- [ ] middleware의 matcher가 보호하려는 경로 집합을 실제로 덮는가 (보호 대상 페이지 목록과 대조)
#### 상태 머신 정합성
- [ ] 정의된 모든 상태 전이가 코드에서 실행됨 (죽은 전이 없음)
- [ ] 코드의 모든 status 업데이트가 전이 맵에 정의됨 (무단 전이 없음)
- [ ] 중간 상태에서 최종 상태로의 전환이 누락되지 않음
- [ ] 프론트의 상태 기반 분기(if status === "X")에서 X가 실제 도달 가능
- [ ] 폴링·구독으로 상태를 기다리는 화면에 종료 조건과 타임아웃이 있음 (영원한 대기 방지)
#### 데이터 흐름 정합성
- [ ] DB 스키마 필드명과 API 응답 필드명의 매핑이 일관됨
- [ ] 프론트 타입 정의와 API 응답의 필드명이 일치
- [ ] 옵셔널 필드의 null/undefined 처리가 양쪽에서 일관됨
- [ ] 목록 응답의 빈 배열과 null이 프론트에서 같은 분기로 처리되는지 확인
- [ ] 날짜·숫자의 직렬화 형식(ISO 문자열 / epoch / Date 객체)이 API 경계 양쪽에서 일치
#### 서버/클라이언트 경계
- [ ] "use client" 컴포넌트가 서버 전용 모듈(fs, DB 클라이언트, 서버 SDK)을 import하지 않음
- [ ] 클라이언트에서 참조하는 환경변수가 전부 NEXT_PUBLIC_ 접두사를 가짐 (없으면 런타임 undefined)
- [ ] 서버 전용 비밀(API 키·DB URL)이 클라이언트 번들 경로에 등장하지 않음
- [ ] 데이터 신선도 기대와 캐시 설정(revalidate / cache / dynamic)이 일치
#### 적대적 검사 (논문 §XIV(한계))
- [ ] 과거 실패 7건 픽스처가 스위트에서 실패로 잡히는가
- [ ] 통과율 100%가 연속되면 센서 난이도를 의심했는가
```

**미검증을 통과로 집계하지 마라.** 검사 도구가 없어 확인하지 못한 항목은 실패도 통과도 아니라 **미검증**이며, 보고서 헤더의 `통과 N / 실패 N / 미검증 N`에 그대로 드러나야 한다(`verifier-agent.md` 7절).

## 3. 검증자 정의의 웹 인스턴스

`verifier-agent.md` 9절 템플릿의 「검증 방법: 양쪽 동시 읽기」 표를 Next.js로 채운 판이다. 검증자 정의 파일에 이 표를 그대로 넣는다.

| 검증 대상 | 왼쪽(생산자) | 오른쪽(소비자) |
|---|---|---|
| API 응답 shape | `route.ts`의 `NextResponse.json()` | `hooks/`의 `fetchJson<T>` |
| 라우팅 | `src/app/` page 파일 경로 | `href`, `router.push` 값 |
| 상태 전이 | `STATE_TRANSITIONS` 맵 | `.update({ status })` 코드 |
| DB → API → UI | 테이블 컬럼명 | API 응답 필드 → 타입 정의 |
| 서버/클라 경계 | `"use client"` 지시자 위치 | import 그래프의 서버 전용 모듈 |
| 환경변수 | `.env*` / 배포 설정의 키 목록 | `process.env.*` 참조 지점 |

**검증 우선순위도 웹에서는 순서가 다르다.** 경계면 교차 비교(A~D)를 먼저 전부 돌리고 나서 코드 품질을 본다 — 위 4종이 런타임 에러의 대부분을 만들고, 코드 품질 지적은 린터가 이미 하고 있기 때문이다. 린터가 하는 일을 검증자가 반복하는 것은 비용만 늘린다.

## 4. 웹 특화 버그 패턴 6종

`verifier-agent.md` 4절의 7개 사례가 **웹에서 어떤 모습으로 나타나는지**의 목록이다. 클래스는 그쪽에 있고, 여기 있는 것은 증상 카탈로그다 — 검증자가 무엇을 grep할지 정할 때 쓴다.

| 패턴 | 증상 | 검사 |
|---|---|---|
| **래핑 불일치** | `x?.filter is not a function` / `.map of undefined` | (A). API가 `{key: [...]}`인데 훅 제네릭이 배열 |
| **route group 접두사 누락** | 특정 구역의 링크가 전부 404 | (B). `(dashboard)` 그룹은 URL에서 사라지지만 실제 경로엔 `/dashboard`가 남는 구성에서 반복 발생 |
| **케이스 변환 누락** | 값이 `undefined`인데 에러는 없음 (이미지 안 뜸, 빈 문자열) | DB `snake_case` → API → 프론트 `camelCase` 경로에서 변환이 한 단계 빠짐 |
| **비동기 계약 혼동** | 202 응답 객체에서 최종 결과 필드 접근 → 크래시 | (A) 주의 항목. 즉시 응답과 완료 응답을 같은 타입으로 선언한 경우 |
| **고아 엔드포인트** | 기능이 "저장 안 됨" — 에러도 없음 | (D). API는 있고 부르는 훅이 없다. 빌드·린트·타입 전부 통과한다 |
| **전이 누락으로 인한 영구 대기** | 진행 화면이 끝나지 않음 | (C). 중간 상태에서 최종 상태로 가는 `.update`가 어디에도 없다 |

**여섯 패턴 전부 빌드를 통과한다.** 그래서 "빌드 됐으니 됐다"가 이 클래스에서 가장 비싼 문장이다. 여섯 개 모두 `rg` 한두 줄로 잡히므로, LLM 심판을 붙이기 전에 이 검사부터 스크립트로 만든다(`verifier-agent.md` 10절 승격 규칙).
