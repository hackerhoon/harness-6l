# 검증자 에이전트 (Independent Verifier)

**경계면 결함을 잡는 계산적 센서를 어떻게 설계하고, 그것을 실행할 독립 검증자를 어떻게 정의하는가.**
실제 프로젝트(SatangSlide)에서 관측된 7개 버그가 이 문서의 모든 규범의 근거다 — 논문 §III(가이드)이 요구하는 "구체적 과거 실패"의 실물이다. 버그는 웹 스택에서 나왔지만 **실패 클래스는 스택과 무관하다.**
이전 판(QA 에이전트 가이드)에는 **두 건의 오분류**가 있었다. 먼저 고쳐라.

| 오분류 | 이전 판 | 정정 |
|---|---|---|
| 센서 분류 | 경계면 교차 비교를 "QA 에이전트의 판단"으로 취급 | **계산적 센서다**(논문 §IV(센서)). grep 기반 결정적 검사이며 LLM 심판보다 **먼저** 해야 할 일 → 1절 |
| 검증자 권한 | "`Explore`는 스크립트를 못 돌리니 `general-purpose`를 써라" = Edit/Write 보유 | **쓰기 금지**(논문 §XVII(다중 에이전트)). 실행 권한과 수정 권한은 다르다. 검증자는 다시 쓰지 않고 **실패를 보고**한다 → 2절 |

> **이 문서는 스택 중립이다.** 웹(Next.js/React) 프로젝트를 검증한다면 구체적 검사 레시피와 25항목 체크리스트가 있는 **`verifier-web-checklist.md`를 이어서 읽어라.** 다른 스택이면 8절의 범용 체크리스트를 그 스택의 어휘로 인스턴스화한다.

## 목차

1. 이것은 계산적 센서다 (논문 §IV(센서))
2. 독립 검증자 규범 — 생산자 편향 (논문 §XVII(다중 에이전트))
3. 경계면 교차 비교 — 핵심 방법론
4. 실제 실패 사례 7건과 실패 클래스 (논문 §IX(개선 루프) Table IX)
5. 적대적 검사 원칙 (논문 §XIV(한계))
6. 점진적 검증 — 자기검증 패턴 (논문 §IV(센서))
7. 실패 보고 포맷 — 검증자 → 라우터 6필드
8. 범용 검증 체크리스트
9. 검증자 에이전트 정의 템플릿 + 예산 레버
10. 계산적 → 추론적 승격 규칙 (논문 §IV(센서))

## 1. 이것은 계산적 센서다 (논문 §IV(센서))

| 논문 §IV(센서) Table III | 계산적 센서 | 추론적 센서 |
|---|---|---|
| 예 | 린터·타입체커·유닛테스트·스키마 검증·**grep 교차 대조** | LLM-as-judge, AI 코드리뷰 |
| 성질 | 빠름 · 무료 · **결정적** | 느림 · 비쌈 · **비결정적** |

이 문서의 **경계면 교차 비교**(생산자가 내보내는 계약과 소비자가 기대하는 계약을 동시에 읽고 대조)는 `grep` → 목록 추출 → 1:1 대조로 끝난다.
사람의 취향도 모델의 판단도 들어가지 않는다. **따라서 계산적 센서다.**

**왜 이 구분이 중요한가.** 논문 §IV(센서)의 설계 원칙이 "**계산적 센서 우선**"이기 때문이다. 이 방법론은 비싼 LLM 심판을 붙이기 **전에** 해야 하는 일이다.
7건의 버그 중 하나도 "코드가 아름다운가"를 묻지 않는다 — 전부 "왼쪽 문자열과 오른쪽 문자열이 같은가"를 묻는다.
이 검사를 건너뛰고 심판부터 다는 것은 논문 §XIV(한계) Table XV가 지목한 흔한 실수 그 자체다("계산적 센서 없음 → 비싼 LLM 심판 → **린터·테스트 먼저**").
**따라서 이 검사들은 궁극적으로 스크립트가 되어야 한다.** 에이전트가 매번 판단으로 수행하는 동안은 과도기이며,
동일 검사가 3회 이상 값을 낳으면 스크립트로 굳히고 CI에 걸어라(논문 §IX(개선 루프)의 3회 규칙 — 상세는 `ratchet.md`).

## 2. 독립 검증자 규범 — 생산자 편향 (논문 §XVII(다중 에이전트))

> 아티팩트를 생산한 에이전트가 그 품질의 유일한 심판이어서는 안 된다. **생산자 편향은 실재한다.**
> 검증자는 출력을 **조용히 다시 쓰지 않고 실패를 보고**한다.
> 라우터가 실패 증거를 생산자에게 되돌리거나 재시도 예산 소진 후 에스컬레이션한다. — 논문 §XVII(다중 에이전트)

파생되는 네 가지 강제 규범:
1. **검증자는 생산자와 분리된 에이전트다.** 백엔드 에이전트가 자기 API를 검증하지 않는다.
2. **Edit/Write를 주지 마라.** 검사 스크립트를 *실행*할 권한(Bash)과 산출물을 *수정*할 권한은 다르다. 이전 판의 추론은 전제(스크립트 실행 필요)가 맞고 결론(쓰기 권한 부여)이 틀렸다.
   **정답: `tools`에 Read/Grep/Glob/Bash를 주고 Edit/Write는 뺀다. `permissionMode: dontAsk`(allow에 없으면 자동 거부 = 최소권한).**
3. **검증자가 고치면 증거가 사라진다.** 조용히 고쳐진 버그는 가이드 규칙도 센서도 만들어내지 못한다. 실패는 래칫의 연료다(논문 §IX(개선 루프)). 검증자가 먹어버리면 하네스가 자라지 않는다.
4. **경로는 검증자 → 라우터(오케스트레이터) → 생산자다.** 검증자가 생산자에게 직접 수정을 명령하지 않는다.
   이전 판의 "발견 즉시 해당 에이전트에게 구체적 수정 요청"은 **정정 대상**이다. 재시도 예산(`maxTurns`) 소진 시 라우터가 인간에게 에스컬레이션한다.

**검증자의 산출물은 수정된 코드가 아니라 실패 보고서다**(7절).

## 3. 경계면 교차 비교 — 핵심 방법론

### 3-1. 존재 확인이 아니라 교차 비교다

가장 빈번한 결함은 두 컴포넌트가 각각 "올바르게" 구현됐지만 **연결 지점에서 계약이 어긋나는 것**이다. 개별로 보면 둘 다 통과한다 — 그래서 개별 검증은 이 클래스를 원리적으로 못 잡는다.

| 경계면 유형 (스택 무관) | 놓치는 이유 |
|---|---|
| 생산자의 반환 구조 → 소비자의 기대 타입 | 각각 개별 검증하면 정상, 교차 비교를 안 함 |
| 필드명·키 이름 → 소비 측 참조 | 이름 변환(케이스·접두사)이 한쪽에만 적용됨 |
| 리소스 실체(파일·경로·테이블) → 참조 문자열 | 참조를 실체 목록과 대조하지 않음 |
| 상태 전이 정의 → 실제 전이를 수행하는 코드 | 정의의 **존재**만 확인하고 실행 코드를 추적하지 않음 |
| 공개된 진입점 목록 → 호출자 목록 | 1:1 매핑을 만들지 않아 "아무도 안 부르는 진입점"이 남음 |
| 즉시 응답 → 최종 결과 (비동기 계약) | 동기/비동기 구분 없이 형태만 확인 |
| 설정 키 정의 → 설정 키 참조 | 정의만 있고 안 읽는 키, 읽지만 정의 없는 키 |

| 약한 체크리스트(존재 확인) | 강한 체크리스트(교차 비교) |
|---|---|
| 진입점이 존재하는가? | 반환 구조와 호출측 기대 타입이 필드 단위로 일치하는가? |
| 상태 전이 정의가 있는가? | 모든 전이 실행 코드가 정의된 전이와 일치하는가? |
| 리소스 파일이 존재하는가? | 코드 내 모든 참조가 실제 존재하는 리소스를 가리키는가? |
| 타입 검사를 켰는가? | 캐스팅·`any`·동적 접근으로 우회된 타입 안전성이 없는가? |

### 3-2. 왜 빌드와 정적 리뷰로 못 잡나

- **타입 시스템의 한계**: 제네릭·캐스팅·`any`·동적 언어의 덕 타이핑이 끼면 컴파일러는 계약 불일치를 볼 수 없다. 선언된 타입은 개발자의 **주장**이지 런타임의 사실이 아니다.
- **빌드 통과 ≠ 정상 동작**: 빌드는 "문법과 선언이 일관된가"를 묻고, 경계면 검사는 "선언이 실제 데이터와 일치하는가"를 묻는다. 다른 질문이다.
- **존재 검증 ≠ 연결 검증**: "이 함수가 있는가"와 "이 함수의 반환이 호출측 기대와 일치하는가"는 전혀 다른 질문이다.

### 3-3. 결정적 검사 3단계

어떤 스택이든 경계면 검사는 같은 세 단계다. **양쪽을 동시에 열어** 대조한다 — 한쪽만 읽으면 이 클래스는 원리적으로 안 잡힌다.

```
1) 추출  — 경계 양쪽의 목록을 각각 기계적으로 뽑는다 (grep/ripgrep/AST 덤프/스키마 덤프)
           왼쪽 = 생산자가 실제로 내보내는 것,  오른쪽 = 소비자가 실제로 기대하는 것
2) 정규화 — 양쪽을 비교 가능한 형태로 맞춘다 (케이스 변환, 접두사 제거, 경로 패턴화, 정렬)
           **정규화 규칙 자체가 계약이다.** 규칙을 문서화하지 않으면 대조 결과를 재현할 수 없다
3) 대조  — 1:1로 맞춘다. 결과는 세 부류다
           왼쪽에만 있음 = 아무도 안 쓰는 것 (의도적인지 누락인지 판정만 사람 몫)
           오른쪽에만 있음 = 존재하지 않는 것을 참조 (거의 항상 버그)
           양쪽에 있으나 형태 불일치 = 계약 위반 (가장 조용하고 가장 비쌈)
```

**출력은 목록이지 의견이 아니다.** 세 부류 중 어디에 몇 건이 들어갔는지가 곧 실패 보고서의 본문이 된다. 이 절차가 3회 이상 값을 내면 스크립트로 굳혀 CI에 건다.

> 웹(Next.js/React) 스택의 구체적 추출·정규화 명령 4종(A. 응답 shape ↔ 훅 타입 / B. 파일 경로 ↔ 링크 / C. 상태 전이 맵 ↔ 업데이트 코드 / D. 엔드포인트 ↔ 훅 1:1)은 **`verifier-web-checklist.md` 1절**에 있다. 다른 스택이면 위 3단계를 그 스택의 도구로 인스턴스화하고, 만든 명령을 프로젝트 가이드에 적어 다음 검증자가 재사용하게 한다.

## 4. 실제 실패 사례 7건과 실패 클래스 (논문 §IX(개선 루프) Table IX)

이 가이드의 모든 규범은 아래 7건에서 추출됐다. **각 사례에 실패 클래스와 지정된 강한 수정을 붙인다.** 클래스가 곧 처방이다 — 증상이 아니라 클래스를 고쳐라(`ratchet.md` 6단계 루프의 2단계).
사례는 웹 프로젝트에서 나왔지만 **클래스는 범용이다.** 왼쪽 열의 증상이 아니라 오른쪽 두 열을 읽어라.

| # | 버그 | 경계면 | 원인 | 실패 클래스 | 강한 수정 |
|---|---|---|---|---|---|
| 1 | `projects?.filter is not a function` | 반환구조→소비타입 | API가 `{projects:[]}` 반환, 훅이 배열 기대 | **알려진 나쁜 패턴** | 센서: 반환 구조 ↔ 선언 타입 스키마 검증 |
| 2 | 대시보드 모든 링크 404 | 리소스→참조 | `/dashboard/` 접두사 누락 | **컨텍스트 누락** | 가이드 항목(경로 규약) + 참조 대조 센서 |
| 3 | 테마 이미지 안 보임 | 필드명→소비 | `thumbnailUrl` vs `thumbnail_url` | **알려진 나쁜 패턴** | 센서: 케이스 변환 린터 규칙 |
| 4 | 테마 선택 저장 안 됨 | 진입점→호출자 | select-theme API 존재, 호출 훅 없음 | **품질 드리프트** | 센서: 진입점↔호출자 1:1 매핑 자동 검사 |
| 5 | 생성 페이지 영원히 대기 | 상태전이→코드 | `template_approved` 전이 코드 누락 | **상태 소실** | 센서: 전이 완전성(죽은 전이/무단 전이) 검사 |
| 6 | `data.failedIndices` 크래시 | 비동기 계약 | 백그라운드 결과를 즉시 응답(202)에서 접근 | **컨텍스트 누락** | 가이드 항목(비동기 계약 명시) + 형태 대조 센서 |
| 7 | 완료 후 결과 보기 404 | 리소스→참조 | `/projects/` → `/dashboard/projects/` | **알려진 나쁜 패턴**(#2 재발) | 센서로 전환 — 3회 규칙 발동 |

- **#2와 #7은 같은 클래스의 재발이다.** 논문 §IX(개선 루프)의 3회 규칙: 1회차=가이드 규칙 추가, 2회차=규칙이 읽히는지 검증, 3회차=**위반 출력을 차단하는 센서로 전환**, 4회차는 절대 없어야 한다. #7 시점에 참조 대조는 이미 센서였어야 한다.
- **#5의 "상태 소실"은 세션 간이 아니라 작업 내 소실이다.** 상태 머신이 중간 상태에 갇혀 전진하지 않았다. Table IX가 지정한 강한 수정은 파일 기반 체크포인트이며, 여기서는 그 결정적 사촌인 전이 완전성 검사다.
- **7건 전부 grep으로 잡힌다.** 하나도 LLM 심판을 요구하지 않는다. 10절 승격 규칙의 증거다.

## 5. 적대적 검사 원칙 (논문 §XIV(한계))

> **매 실행 100% 통과하는 테스트 스위트는 의심스럽다.** 테스트가 너무 쉽거나, 에이전트가 문제를 풀지 않고 테스트를 통과하는 출력을 만드는 법을 배운 것이다.

| 적대적 유형 | 해당 사례 |
|---|---|
| 맞아 보이지만 숨은 위반이 있는 입력 | **#1** — 캐스팅된 제네릭이 컴파일을 통과한다. 타입 검사는 초록불이고 런타임은 죽는다 |
| 스키마 검증은 통과하지만 틀린 데이터인 출력 | **#3** — 필드는 존재하고 문자열이며 이름만 다르다 / **#6** — 즉시 응답은 유효한 JSON이고 필요한 필드가 없을 뿐이다 |
| 빌드되고 린트를 통과하지만 로직 에러인 코드 | **#4** — 호출자가 없어도 빌드된다. 어떤 센서도 건드리지 않고 사용자에게 도달한 조용한 회귀다 / **#5** — 정의도 코드도 각각 유효하다 |

**규범: 센서 스위트는 좋은 포맷을 확인하는 것이 아니라 나쁜 작업을 거부해야 한다.**

- 통과율이 계속 100%면 **센서를 의심하라.** 7건을 재현한 픽스처를 스위트에 넣고 **실패로 잡히는지** 확인하라. 안 잡히면 센서가 아니라 장식이다.
- 새 센서를 추가할 때 **그 센서가 잡았어야 할 과거 실패를 최소 1건 지정하라.** 못 하면 근거 없이 추가된 것이다(논문 §XI(결정 프레임워크) "실제 증거에서 하네스가 자라게 하라").
- 미검증 항목을 통과로 집계하지 마라. 보고서는 **통과 / 실패 / 미검증**을 분리한다(논문 §V(에이전틱 루프) "부분 실패를 유창한 답변 뒤에 숨기지 마라").

## 6. 점진적 검증 — 자기검증 패턴 (논문 §IV(센서))

**검증을 "전체 완성 후 1회"로 배치하지 마라. 각 모듈 완성 직후에 실행하라.** 전체 완성 후 1회면 버그가 누적되어 수정 비용이 커지고, 초기 경계면 불일치가 후속 모듈에 전파된다(#2 → #7이 정확히 이 경로다).
이것은 취향이 아니라 논문 §IV(센서)의 **자기검증 패턴**과 동일한 규범이다 — "각 단계 후 사전 정의된 검사를 실행하고 실패를 에러 텍스트와 함께 되먹인다."

`verified_step` 의사코드의 **정본은 `layers.md`의 「자기검증 패턴 — 가장 강한 하네스 패턴」 한 곳**이다. 여기서 복제하지 않는다. 다만 이 문서의 맥락에서 한 가지를 못 박는다 — **의사코드의 `agent.fix`는 검증자가 아니라 생산자를 가리킨다**(2절). 검증자가 fix를 수행하는 순간 그 루프는 자기검증이 아니라 자기 확인이 된다.

| 이 문서의 용어 | 논문 §IV(센서) |
|---|---|
| 점진적 검증(incremental QA) | 자기검증 패턴 — 각 단계 후 검사 실행 |
| 각 모듈 완성 즉시 그 모듈의 경계면 교차 검증 | 사전 정의된 검사 스위트 실행 |
| 실패 보고서를 라우터에 반환(7절) | 실패를 에러 텍스트와 함께 되먹임 |
| `maxTurns` 소진 후 인간 호출 | `escalate(task, verdict)` |

## 7. 실패 보고 포맷 — 검증자 → 라우터 6필드

논문 §XVII(다중 에이전트): **"완료, 좋아 보임" 같은 자유 형식 요약은 프로덕션 워크플로를 전진시켜서는 안 된다.** 수신자(라우터·생산자)가 **아티팩트를 열어 독립적으로 재현**할 수 있어야 한다.
**최소 필드 6개. 하나라도 비면 그 항목은 미검증으로 분류한다.**

> **「실패 보고」와 「핸드오프」는 다른 포맷이다.** 실패 보고는 **검증자 → 라우터** 방향이고 아래 6필드를 쓴다. 핸드오프는 **생산자 → 수신자** 방향이고 작업 정체성·아티팩트 포인터·증거·가정·기한·미해결의 6필드를 쓴다(`multi-agent.md` 9절). 필드 수가 같을 뿐 목적도 방향도 다르다 — 검증자가 핸드오프 포맷을 쓰면 "증거" 칸에 자기 판정을 적게 되고, 그 순간 생산자 편향이 되돌아온다.

```markdown
## FAIL-{n}
- 검사 대상: {경로}:{줄번호}          ← 경계면이면 양쪽 두 줄을 다 적는다
- 기대: {계약이 요구하는 값·형태·경로}
- 실제: {코드에 있는 값·형태·경로}
- 재현: {그대로 붙여 실행 가능한 명령 — grep 한 줄 또는 테스트 명령}
- 실패 클래스: {알려진 나쁜 패턴 | 컨텍스트 누락 | 잘못된 도구 사용 | 품질 드리프트 | 상태 소실 | 안전하지 않은 행동 | 비용 초과 | 센서 미실행/허위 완료 보고}
- 제안 수정 계층: {가이드 | 센서 | 도구 | 권한 | 환경}   ← 논문 §IX(개선 루프) Table X 사다리에서 가장 강한 계층
```

작성 예(사례 #1):
```markdown
## FAIL-1
- 검사 대상: src/app/api/projects/route.ts:42 ↔ src/hooks/useProjects.ts:11
- 기대: 훅이 fetchJson<{ projects: SlideProject[] }> 로 받고 .projects를 꺼낸다
- 실제: route는 { projects: [...] } 반환, 훅은 fetchJson<SlideProject[]> — 배열로 캐스팅
- 재현: rg -n "NextResponse.json\(" src/app/api/projects/route.ts; rg -n "fetchJson<" src/hooks/useProjects.ts
- 실패 클래스: 알려진 나쁜 패턴 / 제안 수정 계층: 센서(반환 구조 ↔ 선언 타입 검증을 CI에 추가)
```

보고서 헤더는 항상 `통과 N / 실패 N / 미검증 N` 집계로 시작한다.

**보고서는 검증자의 반환 메시지로 낸다. 검증자는 파일을 쓰지 않는다.**
검증자에게서 `Edit`/`Write`를 뺐으면서 보고서 파일 저장을 요구하면, 검증자는 `Bash`로 파일을 쓰게 되고 그 순간 `disallowedTools`는 장식이 된다 — 무제한 쓰기 통로가 열린 것이다. 권한 문법으로 "이 경로에만 쓰기 허용"을 만들 수도 없다: 규칙 평가는 deny→ask→allow 첫 매치 확정이라 **deny 규칙에 예외를 담을 수 없기 때문이다**(`enforcement.md`의 평가 순서 절).
보고서를 파일로 남겨야 하면 **라우터(오케스트레이터)가 검증자의 반환값을 받아 쓴다.** 생산자도 검증자도 아닌 제3자가 쓰는 것이 증거 보존에도 맞다.

## 8. 범용 검증 체크리스트

**어느 스택에서든 결정적으로 검사 가능한 항목만** 담았다. 검증자 정의에 그대로 붙여 쓰고, 프로젝트 어휘로 인스턴스화한다(무엇이 "생산자"이고 무엇이 "소비자"인지만 채우면 된다). 각 항목은 3-3의 3단계 절차로 검사된다.

```markdown
#### 계약 정합성
- [ ] 생산자가 실제로 반환하는 구조와 소비자가 선언한 타입·스키마가 **필드 단위로** 일치
- [ ] 함수·API·CLI의 시그니처(인자 개수·순서·타입)가 **모든** 호출 지점과 일치
- [ ] 경계를 넘는 이름 변환 규칙(케이스·접두사·별칭)이 양쪽에 일관되게 적용
- [ ] 동기/비동기 계약이 구분됨 — 즉시 응답과 최종 결과가 같은 타입으로 취급되지 않음
#### 참조 정합성
- [ ] 코드가 참조하는 파일·경로·리소스가 실제로 존재 (dangling 참조 0건)
- [ ] 설정 키(환경변수·config 필드)의 정의 지점과 참조 지점이 1:1 — 정의만 있고 안 읽는 키, 읽지만 정의 없는 키를 각각 목록화
- [ ] 공개된 진입점 중 어떤 소비자도 호출하지 않는 것을 목록화하고, 의도적인지 누락인지 판정
#### 상태·에러 경로
- [ ] 정의된 모든 상태 전이가 코드에 존재(죽은 전이 없음)하고, 코드의 모든 전이가 정의에 존재(무단 전이 없음)
- [ ] 중간 상태에서 최종 상태로 가는 전이가 누락되지 않음 (작업이 갇히지 않음)
- [ ] 에러·실패 경로가 삼켜지지 않고 호출자에게 도달 — 빈 catch, 무시된 반환 코드, 로그만 찍고 계속 진행하는 지점을 목록화
#### 센서 자산
- [ ] 각 경계면마다 계약 테스트가 최소 1개 존재하고, 계약을 일부러 깨면 그 테스트가 **실패한다**
- [ ] 과거 실패를 재현한 픽스처가 스위트에서 실패로 잡히는가
- [ ] 통과율 100%가 연속되면 센서 난이도를 의심했는가
```

> 웹(Next.js/React)이면 위 항목을 스택 어휘로 펼친 **25항목 체크리스트가 `verifier-web-checklist.md` 2절**에 있다. 그쪽을 쓰고 여기 항목은 커버리지 확인용으로만 본다.

## 9. 검증자 에이전트 정의 템플릿 + 예산 레버

```markdown
---
name: verifier-integration
description: "경계면 교차 비교 전문 검증자. 결정적 검사를 실행하고 실패 보고서만 낸다. 수정하지 않는다."
tools: Read, Grep, Glob, Bash
disallowedTools: Edit, Write, NotebookEdit
permissionMode: dontAsk
model: sonnet        # 명시 필수. 기본은 작업에 맞는 최소 모델. 상위 모델은 사유를 적을 때만
maxTurns: 3          # 재시도 상한의 유일한 네이티브 강제 수단
effort: medium
---

# 경계면 검증자
경계면 계약 위반을 **결정적 검사로** 찾아 실패 보고서를 낸다. **산출물을 수정하지 않는다.**

## 검증 우선순위
1. **경계면 교차 비교**(가장 높음) — 런타임 에러의 주요 원인
2. 기능 스펙 준수 — 진입점/상태머신/데이터 모델
3. 데이터 흐름 정합성 / 4. 코드 품질 — 미사용 코드, 명명 규칙

## 검증 방법: "양쪽 동시 읽기"
| 검증 대상 | 왼쪽(생산자) | 오른쪽(소비자) |
|---|---|---|
| 반환 구조 | {생산자가 반환을 만드는 지점} | {소비자가 타입을 선언하는 지점} |
| 리소스 참조 | {실체 목록의 출처} | {참조 문자열이 있는 곳} |
| 상태 전이 | {전이 정의} | {전이를 수행하는 코드} |
| 저장소 → 경계 → 표현 | {스키마 컬럼명} | {경계 응답 필드 → 표현 타입} |
(웹 스택의 실물 표는 `verifier-web-checklist.md` 3절)

## 출력 프로토콜
- 출력은 **실패 보고서 하나**다. 7절의 6필드 포맷을 따른다(핸드오프 포맷과 혼동 금지).
- 헤더에 `통과 N / 실패 N / 미검증 N`. 미검증을 통과로 집계하지 않는다.
- 보고서는 **반환 메시지**로 낸다. 파일 저장이 필요하면 라우터가 한다(7절).
- **생산자에게 직접 수정을 지시하지 않는다.** 라우터(오케스트레이터)에게 보고한다.
- maxTurns 소진 시: 현재까지의 발견 + 미해결 항목 + 정지 사유를 반환한다.
```

**예산 레버 요약.** 상세 문법·우선순위·검증 레시피는 `enforcement.md`를 참조하라.

| 레버 | 역할 | 등급 |
|---|---|---|
| `tools` | 검사 실행에 필요한 최소 도구만 부여 | 강제(서브에이전트) |
| `disallowedTools` | Edit/Write 명시 차단 — 논문 §XVII(다중 에이전트) 규범의 기계적 표현 | 강제(서브에이전트) |
| `permissionMode: dontAsk` | allow에 없으면 자동 거부 = 최소권한 | 강제(서브에이전트) |
| `maxTurns` | 재시도 상한 — 논문 §V(에이전틱 루프) "단계당 재시도"의 **유일한 네이티브 강제 수단** (기본값은 `layers.md` L3) | 강제(서브에이전트) |
| `model` | **명시 필수.** 기본은 작업에 맞는 최소 모델 | 가이드 |
| `effort` | 추론 예산 | 가이드 |

빌트인 타입을 쓰더라도 **에이전트 정의 파일은 필수**이며, Agent 호출에는 항상 `model` 파라미터를 명시한다. 강제되는 것은 *명시성*이지 특정 모델이 아니다.

## 10. 계산적 → 추론적 승격 규칙 (논문 §IV(센서))

**추론적 센서(LLM 심판)는 결정적 규칙으로 표현 불가능한 검사에만 추가한다.** 승격 전 관문:

1. 이 검사를 grep·타입체커·스키마 검증·테스트로 표현할 수 있는가? → **예면 승격 금지.**
2. 그 결정적 검사를 실제로 만들어 3회 이상 돌렸는가? → **아니오면 승격 금지.**
3. 결정적 검사가 놓친 실패가 **구체적 사례로** 있는가? → **없으면 승격 금지**(논문 §XI(결정 프레임워크) 증거 기반).

**센서 경제학(논문 §IV(센서)) — 승격은 공짜가 아니다.**

| | 계산적 | 추론적 |
|---|---|---|
| 단가 | 린터 규칙 1개 = **무료**, 리뷰 코멘트 한 클래스를 영구 제거 | **$10 / run** |
| 일 50회 실행 | **$0 / 일** | **$500 / 일** |
| 결과 | 결정적 — 회귀가 즉시 드러남 | 비결정적 — 같은 입력에 다른 판정 |

7건의 버그 전부가 계산적 센서로 잡힌다. 이 워크로드에서 LLM 심판은 하루 $500을 쓰고 무료로 얻을 수 있었던 결과를 비결정적으로 재생산한다.

**그럼에도 승격한다면 네 가지를 지켜라(논문 §IV(센서)):**
- **게이트가 아니라 비싼 자문 신호로** 다뤄라. LLM 판정으로 파이프라인을 막지 마라.
- 판정을 **로깅**하라.
- **인간 리뷰와의 일치율을 측정**하라. 일치율이 낮은 심판은 노이즈다.
- **패턴이 명확해지면 결정적 검사로 대체**하고 심판을 제거하라. 승격은 종착지가 아니라 임시 상태다.

논문 §XIV(한계)의 경고를 기억하라: 12개 추론적 센서와 3중 LLM 심판은 프로덕션 시스템이 아니라 **안전으로 위장한 병목**이다. 에이전트가 일하는 시간보다 자기 일을 검사하는 시간이 길면 하네스가 너무 무겁다.
