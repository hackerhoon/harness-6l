# 검증자 에이전트 (Independent Verifier)

**경계면 결함을 잡는 계산적 센서를 어떻게 설계하고, 그것을 실행할 독립 검증자를 어떻게 정의하는가.**
실제 프로젝트(SatangSlide)에서 관측된 7개 버그가 이 문서의 모든 규범의 근거다 — 논문 §1이 요구하는 "구체적 과거 실패"의 실물이다.
이전 판(QA 에이전트 가이드)에는 **두 건의 오분류**가 있었다. 먼저 고쳐라.

| 오분류 | 이전 판 | 정정 |
|---|---|---|
| 센서 분류 | 경계면 교차 비교를 "QA 에이전트의 판단"으로 취급 | **계산적 센서다**(§2). grep 기반 결정적 검사이며 LLM 심판보다 **먼저** 해야 할 일 → 1절 |
| 검증자 권한 | "`Explore`는 스크립트를 못 돌리니 `general-purpose`를 써라" = Edit/Write 보유 | **쓰기 금지**(§12). 실행 권한과 수정 권한은 다르다. 검증자는 다시 쓰지 않고 **실패를 보고**한다 → 2절 |

## 목차

1. 이것은 계산적 센서다 (§2)
2. 독립 검증자 규범 — 생산자 편향 (§12)
3. 경계면 교차 비교 — 핵심 방법론
4. 실제 실패 사례 7건과 실패 클래스 (§7 Table IX)
5. 적대적 검사 원칙 (§13)
6. 점진적 검증 — 자기검증 패턴 (§2)
7. 실패 보고 포맷 (타입 있는 핸드오프, §12)
8. 검증 체크리스트 템플릿
9. 검증자 에이전트 정의 템플릿 + 예산 레버
10. 계산적 → 추론적 승격 규칙 (§2)

## 1. 이것은 계산적 센서다 (§2)

| §2 Table III | 계산적 센서 | 추론적 센서 |
|---|---|---|
| 예 | 린터·타입체커·유닛테스트·스키마 검증·**grep 교차 대조** | LLM-as-judge, AI 코드리뷰 |
| 성질 | 빠름 · 무료 · **결정적** | 느림 · 비쌈 · **비결정적** |

이 문서의 **경계면 교차 비교**(API 응답 shape과 프론트 훅 타입을 동시에 읽고 대조)는 `grep` → 목록 추출 → 1:1 대조로 끝난다.
사람의 취향도 모델의 판단도 들어가지 않는다. **따라서 계산적 센서다.**

**왜 이 구분이 중요한가.** §2의 설계 원칙이 "**계산적 센서 우선**"이기 때문이다. 이 방법론은 비싼 LLM 심판을 붙이기 **전에** 해야 하는 일이다.
7건의 버그 중 하나도 "코드가 아름다운가"를 묻지 않는다 — 전부 "왼쪽 문자열과 오른쪽 문자열이 같은가"를 묻는다.
이 검사를 건너뛰고 심판부터 다는 것은 §13 Table XV가 지목한 흔한 실수 그 자체다("계산적 센서 없음 → 비싼 LLM 심판 → **린터·테스트 먼저**").
**따라서 이 검사들은 궁극적으로 스크립트가 되어야 한다.** 에이전트가 매번 판단으로 수행하는 동안은 과도기이며,
동일 검사가 3회 이상 값을 낳으면 스크립트로 굳히고 CI에 걸어라(§7 3회 규칙 — 상세는 `ratchet.md`).

## 2. 독립 검증자 규범 — 생산자 편향 (§12)

> 아티팩트를 생산한 에이전트가 그 품질의 유일한 심판이어서는 안 된다. **생산자 편향은 실재한다.**
> 검증자는 출력을 **조용히 다시 쓰지 않고 실패를 보고**한다.
> 라우터가 실패 증거를 생산자에게 되돌리거나 재시도 예산 소진 후 에스컬레이션한다. — 논문 §12

파생되는 네 가지 강제 규범:
1. **검증자는 생산자와 분리된 에이전트다.** 백엔드 에이전트가 자기 API를 검증하지 않는다.
2. **Edit/Write를 주지 마라.** 검사 스크립트를 *실행*할 권한(Bash)과 산출물을 *수정*할 권한은 다르다. 이전 판의 추론은 전제(스크립트 실행 필요)가 맞고 결론(쓰기 권한 부여)이 틀렸다.
   **정답: `tools`에 Read/Grep/Glob/Bash를 주고 Edit/Write는 뺀다. `permissionMode: dontAsk`(allow에 없으면 자동 거부 = 최소권한).**
3. **검증자가 고치면 증거가 사라진다.** 조용히 고쳐진 버그는 가이드 규칙도 센서도 만들어내지 못한다. 실패는 래칫의 연료다(§7). 검증자가 먹어버리면 하네스가 자라지 않는다.
4. **경로는 검증자 → 라우터(오케스트레이터) → 생산자다.** 검증자가 생산자에게 직접 수정을 명령하지 않는다.
   이전 판의 "발견 즉시 해당 에이전트에게 구체적 수정 요청"은 **정정 대상**이다. 재시도 예산(`maxTurns`) 소진 시 라우터가 인간에게 에스컬레이션한다.

**검증자의 산출물은 수정된 코드가 아니라 실패 보고서다**(7절).

## 3. 경계면 교차 비교 — 핵심 방법론

### 3-1. 존재 확인이 아니라 교차 비교다

가장 빈번한 결함은 두 컴포넌트가 각각 "올바르게" 구현됐지만 **연결 지점에서 계약이 어긋나는 것**이다. 개별로 보면 둘 다 통과한다 — 그래서 개별 검증은 이 클래스를 원리적으로 못 잡는다.

| 경계면 | 놓치는 이유 |
|---|---|
| API 응답 → 프론트 훅 | 각각 개별 검증하면 정상, 교차 비교를 안 함 |
| API 응답 필드명 → 타입 정의 | 제네릭으로 캐스팅하면 컴파일러가 못 잡음 |
| 파일 경로 → 링크 href | 파일 구조와 href를 교차 비교하지 않음 |
| 상태 전이 맵 → 실제 status 업데이트 | 맵 **존재** 확인만 하고 업데이트 코드를 추적하지 않음 |
| API 엔드포인트 → 프론트 훅 | API 목록과 훅 목록을 1:1 매핑하지 않음 |
| 즉시 응답(202) → 비동기 결과 | 동기/비동기 구분 없이 타입만 확인 |

| 약한 체크리스트(존재 확인) | 강한 체크리스트(교차 비교) |
|---|---|
| API 엔드포인트가 존재하는가? | 응답 shape과 대응 훅의 제네릭 타입이 일치하는가? |
| 상태 전이 맵이 정의되어 있는가? | 모든 status 업데이트 코드가 맵의 전이와 일치하는가? |
| 페이지 파일이 존재하는가? | 코드 내 모든 링크가 실제 존재하는 페이지를 가리키는가? |
| TypeScript strict mode인가? | 제네릭 캐스팅으로 우회된 타입 안전성이 없는가? |

### 3-2. 왜 빌드와 정적 리뷰로 못 잡나

- **제네릭의 한계**: `fetchJson<SlideProject[]>()` — 런타임 응답이 `{ projects: [...] }`여도 컴파일 통과.
- **`npm run build` 통과 ≠ 정상 동작**: 캐스팅·`any`·제네릭이 끼면 빌드는 성공하고 런타임에 죽는다.
- **존재 검증 ≠ 연결 검증**: "API가 있는가"와 "API의 응답이 호출측 기대와 일치하는가"는 전혀 다른 질문이다.

### 3-3. 경계면 4종의 결정적 검사 절차

양쪽을 **동시에 열어** 대조한다. 한쪽만 읽으면 이 클래스는 원리적으로 안 잡힌다.

```
(A) API 응답 ↔ 프론트 훅 타입
  rg -n "NextResponse.json\(" src/app/api/ → shape 추출  |  rg -n "fetchJson<" src/hooks/ → 제네릭 T 추출
  → 엔드포인트별 shape ↔ T 1:1 대조. 래핑 확인({ data: [...] }면 훅이 .data를 꺼내는가)
    주의: 페이지네이션({items,total,page}) vs 배열 기대 / snake_case DB → camelCase API → 프론트 타입 / 202 즉시 응답 vs 최종 결과

(B) 파일 경로 ↔ 링크·라우터 경로
  src/app/ 하위 page.tsx 경로 → URL 패턴 생성 ((group) 제거, [param]은 동적 세그먼트)
  rg -nE "href=|router\.push\(|redirect\(" src/ → 링크 값 수집
  → 각 링크가 URL 집합에 존재하는가 대조. route group 접두사(dashboard/ 등) 누락 주의

(C) 상태 전이 맵 ↔ 실제 업데이트 코드
  STATE_TRANSITIONS 맵 → 허용 전이 목록  |  rg -n "status:" src/app/api/ → .update({ status }) 수집
  → 코드에 있고 맵에 없음 = 무단 전이 / 맵에 있고 코드에 없음 = 죽은 전이. 특히 중간 → 최종 상태 전환 누락

(D) API 엔드포인트 ↔ 프론트 훅 1:1 매핑
  route.ts의 HTTP 메서드별 엔드포인트 목록 ↔ use*.ts의 fetch URL 목록
  → 훅이 호출하지 않는 엔드포인트 = "사용 안 됨". 의도적(관리 API)인지 호출 누락인지 판정만 사람 몫, 목록 생성은 결정적
```

## 4. 실제 실패 사례 7건과 실패 클래스 (§7 Table IX)

이 가이드의 모든 규범은 아래 7건에서 추출됐다. **각 사례에 실패 클래스와 지정된 강한 수정을 붙인다.** 클래스가 곧 처방이다 — 증상이 아니라 클래스를 고쳐라(§1 래칫 6단계 중 2단계).

| # | 버그 | 경계면 | 원인 | 실패 클래스 | 강한 수정 |
|---|---|---|---|---|---|
| 1 | `projects?.filter is not a function` | API→훅 | API가 `{projects:[]}` 반환, 훅이 배열 기대 | **알려진 나쁜 패턴** | 센서: 응답 shape ↔ 제네릭 스키마 검증 |
| 2 | 대시보드 모든 링크 404 | 파일경로→href | `/dashboard/` 접두사 누락 | **컨텍스트 누락** | 가이드 항목(route group 규약) + 링크 대조 센서 |
| 3 | 테마 이미지 안 보임 | API→컴포넌트 | `thumbnailUrl` vs `thumbnail_url` | **알려진 나쁜 패턴** | 센서: 케이스 변환 린터 규칙 |
| 4 | 테마 선택 저장 안 됨 | API→훅 | select-theme API 존재, 호출 훅 없음 | **품질 드리프트** | 센서: 엔드포인트↔훅 1:1 매핑 자동 검사 |
| 5 | 생성 페이지 영원히 대기 | 상태전이→코드 | `template_approved` 전이 코드 누락 | **상태 소실** | 센서: 전이 완전성(죽은 전이/무단 전이) 검사 |
| 6 | `data.failedIndices` 크래시 | 즉시응답→프론트 | 백그라운드 결과를 202 즉시 응답에서 접근 | **컨텍스트 누락** | 가이드 항목(비동기 계약 명시) + shape 대조 센서 |
| 7 | 완료 후 슬라이드 보기 404 | 파일경로→href | `/projects/` → `/dashboard/projects/` | **알려진 나쁜 패턴**(#2 재발) | 센서로 전환 — 3회 규칙 발동 |

- **#2와 #7은 같은 클래스의 재발이다.** §7 Cursor 규칙: 1회차=가이드 규칙 추가, 2회차=규칙이 읽히는지 검증, 3회차=**위반 출력을 차단하는 센서로 전환**, 4회차는 절대 없어야 한다. #7 시점에 링크 대조는 이미 센서였어야 한다.
- **#5의 "상태 소실"은 세션 간이 아니라 작업 내 소실이다.** 상태 머신이 중간 상태에 갇혀 전진하지 않았다. Table IX가 지정한 강한 수정은 파일 기반 체크포인트이며, 여기서는 그 결정적 사촌인 전이 완전성 검사다.
- **7건 전부 grep으로 잡힌다.** 하나도 LLM 심판을 요구하지 않는다. 10절 승격 규칙의 증거다.

## 5. 적대적 검사 원칙 (§13)

> **매 실행 100% 통과하는 테스트 스위트는 의심스럽다.** 테스트가 너무 쉽거나, 에이전트가 문제를 풀지 않고 테스트를 통과하는 출력을 만드는 법을 배운 것이다.

| 적대적 유형 | 해당 사례 |
|---|---|
| 맞아 보이지만 숨은 위반이 있는 입력 | **#1** — `fetchJson<T>`가 컴파일을 통과한다. 타입 검사는 초록불이고 런타임은 죽는다 |
| 스키마 검증은 통과하지만 틀린 데이터인 출력 | **#3** — 필드는 존재하고 문자열이며 이름만 다르다 / **#6** — 202 응답은 유효한 JSON이고 필요한 필드가 없을 뿐이다 |
| 빌드되고 린트를 통과하지만 로직 에러인 코드 | **#4** — 훅이 없어도 빌드된다. 어떤 센서도 건드리지 않고 사용자에게 도달한 조용한 회귀다 / **#5** — 맵도 코드도 각각 유효하다 |

**규범: 센서 스위트는 좋은 포맷을 확인하는 것이 아니라 나쁜 작업을 거부해야 한다.**

- 통과율이 계속 100%면 **센서를 의심하라.** 7건을 재현한 픽스처를 스위트에 넣고 **실패로 잡히는지** 확인하라. 안 잡히면 센서가 아니라 장식이다.
- 새 센서를 추가할 때 **그 센서가 잡았어야 할 과거 실패를 최소 1건 지정하라.** 못 하면 근거 없이 추가된 것이다(§9 "실제 증거에서 하네스가 자라게 하라").
- 미검증 항목을 통과로 집계하지 마라. 보고서는 **통과 / 실패 / 미검증**을 분리한다(§3 "부분 실패를 유창한 답변 뒤에 숨기지 마라").

## 6. 점진적 검증 — 자기검증 패턴 (§2)

**검증을 "전체 완성 후 1회"로 배치하지 마라. 각 모듈 완성 직후에 실행하라.** 전체 완성 후 1회면 버그가 누적되어 수정 비용이 커지고, 초기 경계면 불일치가 후속 모듈에 전파된다(#2 → #7이 정확히 이 경로다).
이것은 취향이 아니라 §2 **자기검증 패턴**과 동일한 규범이다 — "각 단계 후 사전 정의된 검사를 실행하고 실패를 에러 텍스트와 함께 되먹인다."

```
verified_step(agent, task, sensors):                 # 논문 §2 자기검증 패턴
  result = agent.execute(task)
  for sensor in sensors:
    verdict = sensor.check(result)
    if not verdict.passed:
      result = agent.fix(result, verdict)            # 고치는 쪽은 생산자다 (§12)
      if not sensor.check(result).passed: return escalate(task, verdict)   # 예산 소진 시
  return result
```

| 이 문서의 용어 | 논문 §2 |
|---|---|
| 점진적 검증(incremental QA) | 자기검증 패턴 — 각 단계 후 검사 실행 |
| 각 API 완성 즉시 해당 API + 훅 교차 검증 | 사전 정의된 검사 스위트 실행 |
| 실패 보고서를 라우터에 반환(7절) | 실패를 에러 텍스트와 함께 되먹임 |
| `maxTurns` 소진 후 인간 호출 | `escalate(task, verdict)` |

**단, `agent.fix`는 검증자가 아니라 생산자를 가리킨다**(2절).

## 7. 실패 보고 포맷 (타입 있는 핸드오프, §12)

§12: **"완료, 좋아 보임" 같은 자유 형식 요약은 프로덕션 워크플로를 전진시켜서는 안 된다.** 수신자(라우터·생산자)가 **아티팩트를 열어 독립적으로 재현**할 수 있어야 한다.
**최소 필드 6개. 하나라도 비면 그 항목은 미검증으로 분류한다.**

```markdown
## FAIL-{n}
- 검사 대상: {경로}:{줄번호}          ← 경계면이면 양쪽 두 줄을 다 적는다
- 기대: {계약이 요구하는 값·shape·경로}
- 실제: {코드에 있는 값·shape·경로}
- 재현: {그대로 붙여 실행 가능한 명령 — grep 한 줄 또는 테스트 명령}
- 실패 클래스: {알려진 나쁜 패턴 | 컨텍스트 누락 | 잘못된 도구 사용 | 품질 드리프트 | 상태 소실 | 안전하지 않은 행동 | 비용 초과}
- 제안 수정 계층: {가이드 | 센서 | 도구 | 권한 | 환경}   ← §7 Table X 사다리에서 가장 강한 계층
```

작성 예(사례 #1):
```markdown
## FAIL-1
- 검사 대상: src/app/api/projects/route.ts:42 ↔ src/hooks/useProjects.ts:11
- 기대: 훅이 fetchJson<{ projects: SlideProject[] }> 로 받고 .projects를 꺼낸다
- 실제: route는 { projects: [...] } 반환, 훅은 fetchJson<SlideProject[]> — 배열로 캐스팅
- 재현: rg -n "NextResponse.json\(" src/app/api/projects/route.ts; rg -n "fetchJson<" src/hooks/useProjects.ts
- 실패 클래스: 알려진 나쁜 패턴 / 제안 수정 계층: 센서(응답 shape ↔ 제네릭 스키마 검증을 CI에 추가)
```

보고서 헤더는 항상 `통과 N / 실패 N / 미검증 N` 집계로 시작한다.

**보고서는 검증자의 반환 메시지로 낸다. 검증자는 파일을 쓰지 않는다.**
검증자에게서 `Edit`/`Write`를 뺐으면서 보고서 파일 저장을 요구하면, 검증자는 `Bash`로 파일을 쓰게 되고 그 순간 `disallowedTools`는 장식이 된다 — 무제한 쓰기 통로가 열린 것이다. 권한 문법으로 "이 경로에만 쓰기 허용"을 만들 수도 없다: 규칙 평가는 deny→ask→allow 첫 매치 확정이라 **deny 규칙에 예외를 담을 수 없기 때문이다**(`enforcement.md`의 평가 순서 절).
보고서를 파일로 남겨야 하면 **라우터(오케스트레이터)가 검증자의 반환값을 받아 쓴다.** 생산자도 검증자도 아닌 제3자가 쓰는 것이 증거 보존에도 맞다.

## 8. 검증 체크리스트 템플릿

검증자 정의에 그대로 붙여 쓰는 웹 애플리케이션용 경계면 체크리스트. 각 항목은 3-3의 결정적 절차로 검사 가능하다.

```markdown
#### API ↔ 프론트엔드 연결
- [ ] 모든 API route의 응답 shape과 대응 훅의 제네릭 타입이 일치
- [ ] 래핑된 응답({ items: [...] })을 훅에서 unwrap하는지 확인
- [ ] snake_case ↔ camelCase 변환이 일관되게 적용
- [ ] 즉시 응답(202)과 최종 결과의 shape이 프론트에서 구분되는지 확인
- [ ] 모든 API 엔드포인트에 대응하는 프론트 훅이 존재하고 실제로 호출됨
#### 라우팅 정합성
- [ ] 코드 내 모든 href/router.push 값이 실제 page 파일 경로와 매칭
- [ ] route group ((group))이 URL에서 제거되는 것을 고려한 경로 검증
- [ ] 동적 세그먼트([id])가 올바른 파라미터로 채워지는지 확인
#### 상태 머신 정합성
- [ ] 정의된 모든 상태 전이가 코드에서 실행됨 (죽은 전이 없음)
- [ ] 코드의 모든 status 업데이트가 전이 맵에 정의됨 (무단 전이 없음)
- [ ] 중간 상태에서 최종 상태로의 전환이 누락되지 않음
- [ ] 프론트의 상태 기반 분기(if status === "X")에서 X가 실제 도달 가능
#### 데이터 흐름 정합성
- [ ] DB 스키마 필드명과 API 응답 필드명의 매핑이 일관됨
- [ ] 프론트 타입 정의와 API 응답의 필드명이 일치
- [ ] 옵셔널 필드의 null/undefined 처리가 양쪽에서 일관됨
#### 적대적 검사 (§13)
- [ ] 과거 실패 7건 픽스처가 스위트에서 실패로 잡히는가
- [ ] 통과율 100%가 연속되면 센서 난이도를 의심했는가
```

## 9. 검증자 에이전트 정의 템플릿 + 예산 레버

```markdown
---
name: verifier-integration
description: "경계면 교차 비교 전문 검증자. 결정적 검사를 실행하고 실패 보고서만 낸다. 수정하지 않는다."
tools: Read, Grep, Glob, Bash
disallowedTools: Edit, Write, NotebookEdit
permissionMode: dontAsk
model: sonnet        # 명시 필수. 기본은 작업에 맞는 최소 모델. 상위 모델은 사유를 적을 때만
maxTurns: 3          # 재시도 상한의 유일한 네이티브 강제 수단
effort: medium
---

# 경계면 검증자
경계면 계약 위반을 **결정적 검사로** 찾아 실패 보고서를 낸다. **산출물을 수정하지 않는다.**

## 검증 우선순위
1. **경계면 교차 비교**(가장 높음) — 런타임 에러의 주요 원인
2. 기능 스펙 준수 — API/상태머신/데이터모델
3. 데이터 흐름 정합성 / 4. 코드 품질 — 미사용 코드, 명명 규칙

## 검증 방법: "양쪽 동시 읽기"
| 검증 대상 | 왼쪽(생산자) | 오른쪽(소비자) |
|---|---|---|
| API 응답 shape | route.ts의 NextResponse.json() | hooks/의 fetchJson<T> |
| 라우팅 | src/app/ page 파일 경로 | href, router.push 값 |
| 상태 전이 | STATE_TRANSITIONS 맵 | .update({ status }) 코드 |
| DB → API → UI | 테이블 컬럼명 | API 응답 필드 → 타입 정의 |

## 출력 프로토콜
- 출력은 **실패 보고서 하나**다. 6필드 타입 핸드오프를 따른다.
- 헤더에 `통과 N / 실패 N / 미검증 N`. 미검증을 통과로 집계하지 않는다.
- 보고서는 **반환 메시지**로 낸다. 파일 저장이 필요하면 라우터가 한다(7절).
- **생산자에게 직접 수정을 지시하지 않는다.** 라우터(오케스트레이터)에게 보고한다.
- maxTurns 소진 시: 현재까지의 발견 + 미해결 항목 + 정지 사유를 반환한다.
```

**예산 레버 요약.** 상세 문법·우선순위·검증 레시피는 `enforcement.md`를 참조하라.

| 레버 | 역할 | 등급 |
|---|---|---|
| `tools` | 검사 실행에 필요한 최소 도구만 부여 | 강제(서브에이전트) |
| `disallowedTools` | Edit/Write 명시 차단 — §12 규범의 기계적 표현 | 강제(서브에이전트) |
| `permissionMode: dontAsk` | allow에 없으면 자동 거부 = 최소권한 | 강제(서브에이전트) |
| `maxTurns` | 재시도 상한 — §3 "단계당 3회"의 **유일한 네이티브 강제 수단** | 강제(서브에이전트) |
| `model` | **명시 필수.** 기본은 작업에 맞는 최소 모델 | 가이드 |
| `effort` | 추론 예산 | 가이드 |

빌트인 타입을 쓰더라도 **에이전트 정의 파일은 필수**이며, Agent 호출에는 항상 `model` 파라미터를 명시한다. 강제되는 것은 *명시성*이지 특정 모델이 아니다.

## 10. 계산적 → 추론적 승격 규칙 (§2)

**추론적 센서(LLM 심판)는 결정적 규칙으로 표현 불가능한 검사에만 추가한다.** 승격 전 관문:

1. 이 검사를 grep·타입체커·스키마 검증·테스트로 표현할 수 있는가? → **예면 승격 금지.**
2. 그 결정적 검사를 실제로 만들어 3회 이상 돌렸는가? → **아니오면 승격 금지.**
3. 결정적 검사가 놓친 실패가 **구체적 사례로** 있는가? → **없으면 승격 금지**(§9 증거 기반).

**센서 경제학(§2) — 승격은 공짜가 아니다.**

| | 계산적 | 추론적 |
|---|---|---|
| 단가 | 린터 규칙 1개 = **무료**, 리뷰 코멘트 한 클래스를 영구 제거 | **$10 / run** |
| 일 50회 실행 | **$0 / 일** | **$500 / 일** |
| 결과 | 결정적 — 회귀가 즉시 드러남 | 비결정적 — 같은 입력에 다른 판정 |

7건의 버그 전부가 계산적 센서로 잡힌다. 이 워크로드에서 LLM 심판은 하루 $500을 쓰고 무료로 얻을 수 있었던 결과를 비결정적으로 재생산한다.

**그럼에도 승격한다면 네 가지를 지켜라(§2):**
- **게이트가 아니라 비싼 자문 신호로** 다뤄라. LLM 판정으로 파이프라인을 막지 마라.
- 판정을 **로깅**하라.
- **인간 리뷰와의 일치율을 측정**하라. 일치율이 낮은 심판은 노이즈다.
- **패턴이 명확해지면 결정적 검사로 대체**하고 심판을 제거하라. 승격은 종착지가 아니라 임시 상태다.

§13의 경고를 기억하라: 12개 추론적 센서와 3중 LLM 심판은 프로덕션 시스템이 아니라 **안전으로 위장한 병목**이다. 에이전트가 일하는 시간보다 자기 일을 검사하는 시간이 길면 하네스가 너무 무겁다.
