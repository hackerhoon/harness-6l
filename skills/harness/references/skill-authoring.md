# 스킬 작성 & 센서 설계 가이드

하네스가 생성하는 스킬을 **쓰는 법**과, 그 스킬이 제대로 동작하는지 **감지하는 법**을 함께 다룬다. 후반부(§8~§15)는 "스킬을 테스트한다"가 아니라 **논문 §2의 센서(피드백 제어)를 설계한다**로 읽어라. 이 관점을 놓치면 매 실행 100% 통과하는 무의미한 스위트가 남는다(§13).

관련 레퍼런스(복제하지 않는다): 강제 문법·hook·권한 `enforcement.md` / 계층 정의 `layers.md` / 개선 루프·승격 `ratchet.md` / 에이전트 팀·핸드오프 `multi-agent.md`.

## 1. 스킬의 자리 — 구조와 frontmatter

스킬은 **어떻게(절차)**를 담고, 에이전트는 **누가(역할·권한)**를 담는다. 이 분리를 지키면 같은 절차를 여러 역할이 재사용할 수 있다.

```
{skill-name}/
├── SKILL.md          필수. frontmatter + 본문. 트리거 시 전량 로드된다
├── scripts/          반복되는 작업의 실행 코드
├── references/       필요할 때만 읽는 상세 문서
└── assets/           템플릿, 스키마, 샘플 파일
```
`SKILL.md`만 필수다. 나머지는 필요할 때 만든다 — 빈 디렉토리를 미리 파지 마라.

### frontmatter 필드

실제 지원되는 필드다. 전부 쓰라는 뜻이 아니라 **모르고 못 쓰는 일이 없게** 나열한다.

| 필드 | 용도 |
|---|---|
| `name` / `description` | 식별자와 트리거 근거. 디렉토리명이 커맨드명을 결정한다. §2 전부가 이 이야기다 |
| `when_to_use` | 트리거 조건을 description에서 분리해 서술 |
| `argument-hint` / `arguments` | 사용자 호출 시 인자 힌트와 정의 |
| `user-invocable` / `disable-model-invocation` | 슬래시 커맨드 노출 여부 / 모델 자동 트리거 차단 |
| `allowed-tools` / `disallowed-tools` | 도구 허용·차단. 권한 프롬프트를 줄이는 지점 |
| `model` / `effort` | 실행 모델과 추론 강도. **명시하는 것**이 규범이고, 특정 모델 강제는 규범이 아니다 |
| `context: fork` / `agent` / `background` | 무거운 단계를 서브에이전트·백그라운드로 격리(§4) |
| `hooks` | 스킬 스코프 hook. 반드시 실행돼야 하는 규칙의 자리 |
| `paths` / `shell` | 경로 스코프(매칭 파일을 만질 때만 로드) / 실행 셸 |
| `metadata` / `license` / `compatibility` | 배포 메타데이터 |

**유일한 하드 캡: `description` + `when_to_use` 합산 1,536자.** 초과하면 스킬 목록에서 잘려 나가고, 잘린 뒷부분은 트리거 판단에 아예 참여하지 못한다. 다른 필드에는 길이 제한이 없다.

**배포 경로 주의:** claude.ai 업로드나 Skills API 경로로 배포하면 허용 필드가 `name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools` **6개뿐**이고 나머지는 하드 에러다. 로컬 사용자 스코프 스킬과 배포용 스킬은 frontmatter가 다를 수 있다는 뜻이다. 배포 계획이 있으면 처음부터 6필드로 설계하라.

## 2. Description — 유일한 트리거 메커니즘

Claude는 스킬 목록에서 `name` + `description`만 보고 사용 여부를 결정한다. 본문이 아무리 훌륭해도 트리거되지 않으면 존재하지 않는 것과 같다.

Claude는 자기 기본 도구로 처리 가능한 단순 작업에는 스킬을 호출하지 않는 경향이 있다 — "이 PDF 읽어줘"는 description이 완벽해도 트리거되지 않을 수 있다. 복잡·다단계·전문적인 작업일수록 확률이 높다. **이 보수성을 보상해야 한다.**

### 작성 원칙

1. **스킬이 하는 일** + **구체적 트리거 상황**을 모두 기술한다.
2. 유사하지만 트리거하면 안 되는 경우의 **경계 조건**을 명시한다.
3. 약간 **"pushy"하게** 쓴다 — "반드시 이 스킬을 사용할 것", "캐주얼하게 언급만 해도".

**좋은 예시**

```yaml
description: "PDF 읽기, 텍스트/테이블 추출, 병합, 분할, 회전, 워터마크, 암호화, OCR 등
  모든 PDF 작업. .pdf 파일을 언급하거나 PDF 산출물을 요청하면 반드시 이 스킬을 사용할 것.
  단순 '읽어달라'가 아닌 변환/편집/분석이 필요할 때 특히 유용."
```
```yaml
description: "엑셀/CSV/TSV의 열 추가, 수식 계산, 서식, 차트, 데이터 정제를 포함한 모든
  스프레드시트 작업. 사용자가 스프레드시트 파일을 언급하면 — 심지어 캐주얼하게
  ('다운로드 폴더의 xlsx')라고만 해도 — 이 스킬을 사용할 것.
  단, DB 쿼리 결과를 표로 보여주는 작업에는 트리거하지 마라."
```

**나쁜 예시** — `"데이터를 처리하는 스킬"`(너무 모호, 어떤 파일·작업인지 불분명) / `"PDF 관련 작업"`(구체적 동작 나열 없음, 트리거 상황 미기술).

### 부정 예시를 반드시 넣어라 (§4)

OpenAI Skill 시스템에서 압축 컨텍스트에 **부정 예시**를 추가한 것만으로 라우팅 정확도가 **73% → 85%**로 올랐다. 논문 전체에서 description 설계에 직접 적용되는 유일한 정량 결과다.

실무 규범: description 끝에 **"이럴 때는 트리거하지 마라"** 한 문장을 붙인다. 위 두 번째 예시의 마지막 줄이 그 형태다. 이 문장은 §11-(b)의 near-miss 쿼리와 **같은 재료**에서 나온다 — near-miss 쿼리를 먼저 쓰고, 그중 가장 헷갈리는 것을 부정 예시로 승격시켜라.

## 3. 본문 작성 5원칙

**① Why를 설명하라.** LLM은 이유를 이해하면 엣지 케이스에서도 옳게 판단한다. 강압적 규칙보다 맥락이 효과적이다.
- 나쁨: `ALWAYS use pdfplumber for table extraction. NEVER use PyPDF2 for tables.`
- 좋음: `테이블 추출에는 pdfplumber를 사용한다. PyPDF2는 텍스트 추출에 특화되어 행/열 구조를 보존하지 못하기 때문이다. pdfplumber는 셀 경계를 인식해 구조화된 데이터를 반환한다.`

**② Lean하게 유지하라.** 컨텍스트 윈도우는 공공재다. 모든 문장에 자문한다 — "Claude가 이미 아는 내용인가?"(삭제) / "이 설명이 없으면 실수하는가?"(유지) / "예시 하나가 긴 설명보다 효과적인가?"(예시로 대체).

**③ 일반화하라.** 피드백이나 센서 결과에서 문제가 발견되면 특정 예시에 맞춘 좁은 수정 대신 원리 수준에서 고친다.
- 오버피팅: `"Q4 매출" 열이 있으면 숫자로 변환하라.`
- 일반화: `열 이름에 "매출", "금액", "수량" 등 수치를 암시하는 키워드가 있으면 숫자 타입으로 변환한다. 변환 실패 시 원본 값을 유지한다.`

**④ 반복 코드는 번들링하라.** 실행마다 같은 헬퍼를 다시 쓰게 만들지 말고 `scripts/`에 미리 넣는다(§5).

**⑤ 명령형으로 작성하라.** "~합니다", "~할 수 있습니다"가 아니라 "~한다", "~하라". 스킬은 설명서가 아니라 지시서다.

**출력 형식과 예시.** 산출물 형식이 중요하면 템플릿을 **정확히 따르라**고 지시하고 실물 예시를 붙인다. 예시는 긴 설명보다 강하다 — 예: `입력: JWT 토큰 기반 사용자 인증 추가 → 출력: feat(auth): JWT 기반 인증 구현`.

## 4. Progressive Disclosure와 크기 관리

### 3단계 로딩

| 단계 | 무엇 | 로드 시점 | 컨텍스트 비용 |
|---|---|---|---|
| 1 | `name` + `description` | 항상(스킬 목록) | 매우 작음. 단 1,536자 캡 적용 |
| 2 | `SKILL.md` 본문 | 스킬 트리거 시 | **전량 로드 — 실질적 비용은 여기서만 발생** |
| 3 | `references/`, `scripts/`, `assets/` | 본문이 읽으라고 지시할 때만 | 읽은 파일만큼만 |

### reference 파일 개수는 컨텍스트 비용이 아니다

3단계는 지시가 있을 때만 로드된다. 따라서 reference를 20개로 쪼개도 컨텍스트는 늘지 않는다. **진짜 리스크는 컨텍스트 폭증이 아니라 라우팅 실패다** — 필요한 파일을 안 읽거나 엉뚱한 파일을 읽는 것.

완화 수단 세 가지:
- 각 reference **상단에 목차(ToC)**를 둔다. 300줄 이상이면 필수.
- SKILL.md에 **"어떤 상황에서 어느 파일"의 결정표**를 둔다. 파일 목록 나열이 아니라 조건 → 파일 매핑이어야 한다.
- 무거운 단계는 `context: fork` + `agent:` frontmatter로 **서브에이전트에 격리**한다. 이러면 그 단계의 컨텍스트를 메인이 아예 소비하지 않는다.

### 크기 규칙

- SKILL.md 본문 목표 **500줄 이내**. 넘으면 3단계로 밀어낸다.
- reference **300줄 이상이면 ToC 필수.**
- 도메인이 갈리면 파일로 분리한다. 예: `SKILL.md`(개요 + 도메인 선택 결정표) + `references/{finance,sales,product}.md`. 매출을 물으면 `finance.md`만 로드된다.
- 조건부 상세도 같은 원리다 (아래는 가상의 문서 스킬 예시): `단순 편집은 XML 직접 수정. **추적 변경이 필요하면** 그때 `references/<해당 주제>.md`를 읽어라.`

## 5. 번들 스크립트와 경로 규칙

**상대경로는 반드시 깨진다** — 세션 셸의 cwd를 따라가기 때문이다. 사용자 스코프 스킬에서는 `${CLAUDE_SKILL_DIR}`를 쓴다.

```
frontmatter: allowed-tools: ["Bash(bash ${CLAUDE_SKILL_DIR}/scripts/analyze.sh:*)"]
본문:        `bash ${CLAUDE_SKILL_DIR}/scripts/analyze.sh <입력파일>` 를 실행한다
```

치환은 **본문과 `allowed-tools`의 Bash 규칙 두 곳 모두**에서 일어난다. 같은 변수를 양쪽에 쓰면 번들 스크립트가 **권한 프롬프트 없이** 실행된다 — 이것이 변수를 쓰는 실질적 이유다. 상세 문법·우선순위는 `enforcement.md`를 참조하라.

**무엇을 번들링할 것인가** — 실행 트랜스크립트를 관찰해 결정한다. 다음 신호가 보이면 번들링 대상이다.

| 신호 | 조치 |
|---|---|
| 3개 실행 중 3개에서 동일한 헬퍼 스크립트를 새로 작성 | `scripts/`에 번들링 |
| 매번 같은 pip/npm install 실행 | 스킬에 의존성 설치 단계 명시 |
| 동일한 다단계 접근법 반복 | 본문에 표준 절차로 기술 |
| 매번 비슷한 에러 후 같은 회피책 적용 | 알려진 문제와 해결법을 본문에 기술 |

번들링한 스크립트는 **반드시 실행 테스트를 거친다.** 실행되지 않는 번들 스크립트는 죽은 경로이며, 1단계 dangling 검사에 걸린다.

## 6. 스킬-에이전트 연결

- **1:1** — 하나의 에이전트가 하나의 전용 절차를 가질 때.
- **1:다** — 하나의 스킬을 여러 에이전트가 공유할 때. 재사용 관점에서 이쪽이 기본값이다.

연결 시 확인할 것:
- 에이전트의 `tools` 권한이 스킬이 요구하는 도구를 포함하는가. 검증 역할 에이전트라면 Edit/Write를 **제외**해야 한다(`multi-agent.md`).
- 스킬이 요구하는 번들 스크립트 실행 권한이 에이전트 쪽에서 막히지 않는가.
- Agent 호출에는 `model` 파라미터를 **명시**한다. 강제되는 것은 명시성이지 특정 모델이 아니다.

## 7. 중복 검토와 재사용 설계

신규 스킬을 만들기 전에 기존 스킬과의 중복을 확인한다. 하네스를 반복 구축하면 기능이 겹치는 스킬이 다른 이름으로 누적된다.

| 상황 | 조치 |
|---|---|
| 기존 스킬이 신규 기능을 완전히 포함 | **신규 생성 금지** — 기존 스킬을 에이전트에 연결 |
| 기존 스킬이 부분 포함이고 일반화 가능 | 기존 스킬을 일반화하여 확장 |
| 도메인 특화가 의도된 부분 포함 | 신규 생성 진행 — 별개 스킬로 유지 |
| 기능 범위가 완전히 다름 | 신규 생성 진행 |

**원칙:** 하나의 스킬이 하나의 역할에 집중할수록 재사용성이 높고 중복이 준다. 역할이 둘 이상이면 분리 가능성을 먼저 검토한다.

### 어디까지 일반화할지

일반화는 무한히 가능하므로 **의도된 책임 범위**에서 멈춘다. 의도된 도메인 특화는 유지하고 우연한 종속만 제거한다.

| 단계 | 결과 |
|---|---|
| "fintech 리스크 평가 PDF"에서 fintech 종속 제거 | "평가 결과 PDF" — 책임 범위가 평가 리포트면 여기서 멈춘다 |
| 평가 종속까지 제거 | "PDF 포매팅" — 이미 존재하면 새로 만들지 말고 재사용 |

책임 범위가 "fintech 리스크 평가"로 의도된 특화라면 일반화하지 않고 별개 스킬로 유지한다. 기존 스킬을 확장하면 **그 스킬에 의존하는 에이전트의 동작이 바뀐다.** 확장 전 의존성을 확인하고, description에 확장된 사용 범위를 반영하며, §15의 트리거 회귀 스위트를 돌린다.

## 8. 센서로서의 스킬 평가 — 계산적 vs 추론적

여기부터가 **L2 센서 설계**다. "스킬을 테스트한다"고 부르지 마라. 만들고 있는 것은 스킬이 조용히 나빠졌을 때 그것을 잡아내는 **피드백 장치**다(§2).

| 센서 유형 | 스킬 평가에서의 구현 | 특성 |
|---|---|---|
| **계산적 센서** | assertion 기반 자동 채점, 스키마 검증, 번들 스크립트 실행 테스트, 파일 존재·형식 검사 | 빠름 · 무료 · 결정적 |
| **추론적 센서** | 사용자 리뷰, LLM 심판, 블라인드 Comparator | 느림 · 비쌈 · 비결정적 |

**설계 원칙 — 계산적 센서 우선.** 결정적 규칙으로 표현 **불가능한** 검사에만 추론적 센서를 추가한다. "이익률 열이 추가되었다"는 계산적 센서로 검증 가능하고 "문체가 자연스럽다"는 아니다. 전자를 LLM 심판에게 맡기는 순간 비용 곡선이 무너진다.

**센서 경제학.** 린터 규칙 하나는 **무료**로 리뷰 코멘트 한 클래스를 영구히 제거한다. LLM 심판은 **$10/run × 50회/일 = $500/일**이다. 계산적 센서가 더 빨리 복리로 쌓인다 — 한 번 쓰면 이후 모든 실행에서 무료로 작동하지만, 추론적 센서는 매 실행마다 다시 결제한다.

**추론적 센서는 게이트가 아니라 비싼 자문 신호다.** 배포 차단 권한을 주지 마라. 대신 (1) 판정을 **로깅**하고 (2) 인간 리뷰와의 **일치율을 측정**하고 (3) 패턴이 명확해지면 **결정적 검사로 대체**한다. §7의 "가이드 → 센서 승격"과 같은 사다리다 — 추론적 센서는 아직 규칙화되지 않은 것의 임시 거처이지 종착지가 아니다.

**점진적 구축.** 이미 있는 것부터 실행 루프에 배선한다. 프로젝트의 테스트·린터·타입체커·빌드 명령이 첫 센서다. 새 평가 프레임워크를 짓기 전에 스킬 산출물에 기존 `npm test`를 돌리는 것부터 한다. 계산적 센서가 안정적으로 에러를 잡기 시작한 뒤에만 추론적 센서를 고려한다.

## 9. 자기검증 패턴

논문이 **가장 강한 하네스 패턴**으로 지목한 것(§2). 에이전트에게 자기 센서 접근권을 주고, 각 단계 후 사전 정의된 검사를 실행해 실패를 **에러 텍스트와 함께** 되먹인다. 핵심은 이것이 **모델이 자기 품질을 판단하는 게 아니라는 점**이다 — 외부의 결정적 검사를 실행하고 그 결과에 반응하는 것이다. 전자는 생산자 편향에 오염되고 후자는 오염되지 않는다.

```
verified_step(agent, task, sensors):
  result = agent.execute(task)
  for sensor in sensors:
    verdict = sensor.check(result)
    if not verdict.passed:
      result = agent.fix(result, verdict)          # verdict의 에러 텍스트를 그대로 전달
      if not sensor.check(result).passed:
        return escalate(task, verdict)             # 재시도 예산 소진 → 에스컬레이션
  return result
```

스킬 본문에 이 패턴을 심는 방법:

```markdown
## 검증
산출물을 생성한 뒤 다음을 실행한다:
`bash ${CLAUDE_SKILL_DIR}/scripts/verify.sh <산출물경로>`

실패하면 **출력된 에러 메시지를 근거로** 수정하고 재실행한다.
2회 재시도 후에도 실패하면 수정하지 말고, 실패한 검사 이름과 에러 원문을
그대로 포함해 보고한다. 부분 실패를 완성된 답변 뒤에 숨기지 마라.
```

마지막 두 문장이 논문 §3의 요구다 — 예산이 소진되면 현재 최선의 산출물 + 완료된 작업 + 미해결 이슈 + 정지 사유를 반환한다.

## 10. 센서 커버리지 테스트 5문항

무인 운영으로 승격하기 전의 **필수 관문**이다(§2). 스킬 하나를 완성했다고 판단하기 전에 답한다.

1. 인간 검사 없이 에이전트가 **자기 출력을 검사할 수 있는가?**
2. 모든 중요 출력에 **계산적 센서가 최소 1개** 있는가?
3. 센서 결과가 **추세 분석용으로 로깅**되는가?
4. 에이전트 동작이 변해도 **센서는 안정적인가?**(구현 세부에 결합되지 않았는가)
5. **어떤 센서도 건드리지 않고** 조용한 회귀가 사용자에게 도달할 수 있는가?

**하나라도 "아니오"(5번은 "예")면 무인 운영 전에 센서를 추가한다.** 이 5문항은 스킬 단위로도, 하네스 전체로도 적용된다.

## 11. 적대적 센서 3자산

**센서 스위트는 좋은 포맷을 확인하는 게 아니라 나쁜 작업을 거부해야 한다**(§13). 매 실행 100% 통과하는 스위트는 의심스럽다 — 검사가 너무 쉽거나, 에이전트가 문제를 실제로 풀지 않고 검사를 통과하는 출력을 만드는 법을 배운 것이다.

### (a) Non-discriminating assertion 경고

좋은 산출물과 나쁜 산출물을 **모두 통과시키는** assertion은 센서가 아니다. 정보량이 0이다.

- 나쁨: `"출력이 존재한다"` — 스킬 유무와 무관하게 항상 통과
- 나쁨: `"잘 작성되었다"` — 주관적 판단 필요, 계산적 센서가 아님
- 좋음: `"E열에 profit_margin_pct 열이 존재하고 값이 내림차순이다"` — 참/거짓 판별 가능, 스킬의 핵심 가치를 검증

**판별 절차:** With-skill과 Baseline 두 구성 모두에서 100% 통과한 assertion을 목록화한다. 그것들은 제거하거나 더 도전적인 것으로 교체한다. 적대적 입력을 의도적으로 섞어라 — 맞아 보이지만 숨은 위반이 있는 입력, 스키마 검증은 통과하지만 데이터가 틀린 출력, 빌드·린트는 통과하지만 로직이 틀린 코드.

### (b) Near-miss 트리거 쿼리

description의 트리거 정확도를 재는 센서. **should-trigger 8~10개 + should-NOT-trigger 8~10개**를 쓴다.

쿼리 품질 기준 — 실제 사용자가 입력할 법한 구체적·자연스러운 문장 / 파일 경로·열 이름·회사명 등 **구체적 디테일** 포함 / 길이·톤·형식을 섞는다.

**Should-trigger:** 같은 의도의 다양한 표현(공식적/캐주얼) / 파일 유형을 명시하지 않지만 분명히 필요한 경우 / 비주류 사용 사례 / 다른 스킬과 경쟁하지만 이 스킬이 이겨야 하는 경우.

**Should-NOT-trigger — near-miss가 핵심이다.** 명백히 무관한 쿼리("피보나치 함수 작성")는 테스트 가치가 **없다.** 아무 description이나 통과시키므로 (a)의 non-discriminating assertion과 같은 병이다. 대신 경계가 모호한 것을 쓴다: 인접 도메인, 키워드는 겹치지만 맥락이 다른 경우, 모호한 표현. 여기서 나온 실패 사례가 §2의 부정 예시 재료가 된다.

기존 스킬과의 충돌도 같은 방식으로 검증한다 — 새 스킬의 should-trigger 쿼리가 기존 스킬을 잘못 트리거하지 않는지 확인하고, 충돌하면 경계 조건을 더 명확히 기술한다.

### (c) 블라인드 Comparator

두 산출물을 A/B로 익명화해 **어느 쪽이 스킬을 쓴 결과인지 모르는 상태로** 품질을 판정한다. 논문 §12 **"생산자 편향은 실재한다"**의 구현이며, 아티팩트를 생산한 주체가 그 품질의 유일한 심판이 되는 것을 막는다.

**유형:** 추론적 센서 — 게이트가 아니라 자문 신호다(§8). **활용 시점:** "새 버전이 정말 더 나은가?"를 엄밀히 확인할 때. 일상적 반복 개선에서는 생략한다. **판정 기준:** 내용(정확성·완성도) / 구조(조직화·포맷·사용성) / 종합. Comparator 판정이 계산적 센서 결과와 반복해서 엇갈리면, 그 차이를 만드는 요인을 assertion으로 뽑아내 결정적 검사로 강등시켜라.

## 12. With-skill vs Baseline 비교 실행

스킬의 **차별적 가치**를 측정하려면 대조군이 필요하다. 단일 실행 결과는 "스킬이 좋았다"와 "모델이 원래 잘한다"를 구분하지 못한다. 각 테스트 프롬프트에 대해 두 서브에이전트를 **동시에** 스폰한다.

```
With-skill: 프롬프트 P + 스킬 경로   → .../eval-{name}/with_skill/outputs/
Baseline:   프롬프트 P (동일), 스킬 없음 → .../eval-{name}/without_skill/outputs/
```

Baseline 선택 — 새 스킬 생성이면 **스킬 없이 같은 프롬프트**, 기존 스킬 개선이면 **수정 전 스킬 버전**(스냅샷 보존).

**테스트 프롬프트 작성** — 실제 사용자가 입력할 법한 **구체적이고 자연스러운 문장**이어야 한다. 추상적 프롬프트("PDF를 처리하라", "데이터를 추출하라")는 가치가 없다.

> "다운로드 폴더의 'Q4_매출_최종_v2.xlsx'에서 C열(매출)과 D열(비용)로 이익률(%) 열을 추가해줘. 그리고 이익률 기준 내림차순 정렬."

2~3개로 시작하되 **핵심 사용 사례 1 + 엣지 케이스 1 + (선택) 복합 작업 1**을 커버한다. 톤(공식/캐주얼), 의도(명시/암시), 난이도(단순/복잡)를 섞고 일부에는 약어·오타를 넣는다.

## 13. 계측 스키마 — L6의 1차 데이터 소스

이 세 스키마는 평가 부산물이 아니라 **관찰가능성(L6)의 1차 데이터 소스**다. 논문 §6의 "비용 귀속은 일별이 아니라 작업별로"를 만족시키는, **이미 존재하는** 계측 자산이다. L6를 백지에서 설계하지 말고 여기부터 배선하라.

### eval_metadata.json — 테스트 케이스 정의

```json
{ "eval_id": 0, "eval_name": "multi-page-table-extraction",
  "prompt": "사용자의 작업 프롬프트",
  "assertions": ["산출물에 X가 포함되어 있다", "Y 형식으로 파일이 생성되었다"] }
```

### grading.json — 계산적 센서의 판정 기록

```json
{ "expectations": [
    { "text": "이익률 열이 추가됨", "passed": true,  "evidence": "E열에 'profit_margin_pct' 확인" },
    { "text": "이익률 기준 내림차순 정렬", "passed": false, "evidence": "정렬 없이 원본 순서 유지됨" }
  ],
  "summary": { "passed": 1, "failed": 1, "total": 2, "pass_rate": 0.50 } }
```

**필드명을 정확히 지켜라:** `text`, `passed`, `evidence`. `name`/`met`/`details` 같은 변형은 금지다 — 스키마가 흔들리면 추세 분석(센서 커버리지 5문항의 3번)이 불가능해진다.

### timing.json — 작업별 비용 귀속

```json
{ "total_tokens": 84852, "duration_ms": 23332, "total_duration_seconds": 23.3 }
```

**캡처 규칙(중요):** 서브에이전트 **완료 알림 시점에만** `total_tokens`와 `duration_ms`에 접근할 수 있고 **이후에는 복구 불가능하다.** 알림을 받는 즉시 저장하라. 놓치면 그 실행의 비용 데이터는 영구히 사라진다.

### 워크스페이스 구조

상태 저장소는 `_workspace/` **하나**다. 별도 저장소를 신설하지 마라.

```
_workspace/skill-evals/{skill-name}/
├── iteration-1/
│   ├── eval-multi-page-table-extraction/     ← 숫자가 아닌 서술적 이름
│   │   ├── eval_metadata.json
│   │   ├── with_skill/{outputs/, timing.json, grading.json}
│   │   └── without_skill/{outputs/, timing.json, grading.json}
│   └── benchmark.json
├── iteration-2/ ...                          ← 이전 iteration 덮어쓰기 금지
└── evals/evals.json
```

**산출물 아티팩트와 계측 파일은 보존한다.** 다만 진행 중 작업의 체크포인트는 활성 작업당 최신 1개만 유지한다 — 낡은 체크포인트는 없어진 파일과 번복된 결정을 가리킨다(§13).

## 14. 반복 개선 루프

```
1. 스킬 수정
2. 새 iteration-N+1/ 에 모든 테스트 케이스 재실행
3. 사용자에게 결과 제시 (이전 iteration과 비교)
4. 피드백 수집  (빈 피드백 = "이상 없음")
5. 다시 수정 → 반복
```

**종료 조건:** 사용자가 만족 / 피드백이 모두 비어 있음 / 의미 있는 개선이 더 이상 없음.

**개선 원칙**

1. **피드백을 일반화하라.** 테스트 예시에만 맞는 좁은 수정은 오버피팅이다. 원리 수준에서 고친다(§3-③). 특정 파일명·열 이름에 반응하는 수정을 넣었다면 그것은 실패다.
2. **무게를 벌지 않는 것은 제거하라.** 트랜스크립트를 읽고, 스킬이 에이전트에게 비생산적 작업을 시키고 있으면 그 부분을 삭제한다.
3. **Why를 이해하라.** 피드백이 한 줄이어도 왜 중요한지 파악하고 그 이해를 스킬에 반영한다.
4. **반복 패턴은 번들링하라.** 모든 실행에서 같은 헬퍼가 생성되면 `scripts/`에 미리 넣는다(§5).
5. **초안 → 재검토.** 한 번에 완벽하게 쓰려 하지 말고, 초안을 쓴 뒤 새로운 시각으로 다시 읽고 고친다.

## 15. 트리거 회귀 스위트

description 수정은 **가장 조용한 회귀 발생원**이다. 본문은 그대로인데 스킬이 더 이상 불리지 않으면, 증상은 "스킬이 나빠졌다"가 아니라 "아무 일도 안 일어난다"로 나타나 아무도 알아채지 못한다.

1. description을 고치기 **전에**, 현재 트리거되는 표현들을 **회귀 스위트로 고정**한다. §11-(b)의 should-trigger 쿼리 집합이 그대로 스위트가 된다.
2. 수정 후 그 표현 전부에 여전히 반응하는지 확인한다.
3. **전부 통과한 뒤에만 배포한다.**
4. description 변경은 **삭제가 아니라 추가를 기본**으로 한다. 문구를 지우는 것은 트리거 표면을 좁히는 행위이며, 지운 문구가 어떤 사용자 표현을 담당했는지는 대개 알 수 없다. 1,536자 캡에 걸려 정말로 지워야 할 때만 지우고, 그때는 지운 표현들을 회귀 스위트에 반드시 넣는다.

이 스위트는 §11-(b)의 near-miss 쿼리와 함께 보관한다 — 하나는 "여전히 트리거되는가", 다른 하나는 "여전히 트리거되지 않는가"를 재는 대칭 센서다.

## 16. 포함하지 않을 것 / 완료 체크리스트

**스킬에 넣지 않을 것:** README·CHANGELOG·INSTALLATION_GUIDE 등 부가 문서 / 스킬 생성 과정의 메타 정보(테스트 결과, 반복 이력 — 그것은 `_workspace/`에 있다) / 사용자 대상 설명서(스킬은 AI 에이전트를 위한 지시서다) / Claude가 이미 아는 일반 지식.

### 완료 체크리스트

- [ ] `description` + `when_to_use` 합산 **1,536자 이내**
- [ ] description에 트리거 상황 + **부정 예시**("이럴 때는 트리거하지 마라") 포함
- [ ] SKILL.md 본문 500줄 이내, 300줄 넘는 reference에 ToC 존재
- [ ] SKILL.md에 "어떤 상황에서 어느 파일"의 결정표 존재
- [ ] 모든 번들 경로가 `${CLAUDE_SKILL_DIR}` 사용, 상대경로 없음
- [ ] `allowed-tools`의 Bash 규칙과 본문의 명령 문자열이 **동일한 변수 표기**
- [ ] 번들 스크립트가 실제로 실행됨(dangling 경로 없음)
- [ ] 중요 출력마다 **계산적 센서 최소 1개**
- [ ] 자기검증 단계가 본문에 심겨 있고, 실패 시 에러 원문을 되먹임
- [ ] non-discriminating assertion 제거 완료(두 구성 모두 100% 통과한 것)
- [ ] should-trigger 8~10 + should-NOT-trigger(near-miss) 8~10 작성
- [ ] 트리거 회귀 스위트 통과
- [ ] `timing.json` / `grading.json` 필드명 스키마 준수
- [ ] 기존 스킬과의 중복 검토 완료
- [ ] 센서 커버리지 5문항 통과(무인 운영으로 승격하는 경우)
