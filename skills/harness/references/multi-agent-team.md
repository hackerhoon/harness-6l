# 다중 에이전트 — 에이전트 팀 모드 (multi-agent-team)

> 이 파일은 실행 모드로 **에이전트 팀**을 선택한 경우에만 읽는다. 선택 기준은 `multi-agent.md` 2절. 서브 에이전트 모드로 설계 중이라면 이 파일은 열지 않는다 — `multi-agent.md` 하나로 충분하다. 여기 있는 것은 `TeamCreate`/`SendMessage`/`TaskCreate`가 실제로 등장하는 구성에서만 쓰이는 내용이며, 모드와 무관한 규범(핸드오프·검증자 독립·에스컬레이션·공유 상태·에러 핸들링)은 전부 `multi-agent.md`에 있고 여기서 반복하지 않는다. 논문 §XVII(다중 에이전트)의 경계 장치 5종은 팀 모드에서도 그대로 요구된다.

## 1. 팀 크기 가이드라인

| 작업 규모 | 권장 팀원 수 | 팀원당 작업 수 |
|---|---|---|
| 소규모 (5~10개 작업) | 2~3명 | 3~5개 |
| 중규모 (10~20개 작업) | 3~5명 | 4~6개 |
| 대규모 (20개+ 작업) | 5~7명 | 4~5개 |

> 팀원이 늘수록 조율 오버헤드가 커진다. **3명의 집중된 팀원이 5명의 산만한 팀원보다 낫다.** 에이전트가 일하는 시간보다 서로를 확인하는 시간이 길어지면 하네스가 너무 무겁다(논문 §XIV(한계)).

## 2. Phase 간 팀 재구성

세션당 1팀만 활성이고 중첩이 불가능하므로, Phase마다 다른 조합이 필요하면 팀을 갈아끼운다. **팀 재구성** — 산출물을 파일로 저장 → `TeamDelete` → 새 `TeamCreate` 순서로 간다. 이전 산출물은 `_workspace/`에 남으므로 새 팀이 `Read`로 접근한다.

팀 모드를 골랐다고 대화가 공유되는 것이 아니라는 원칙(`multi-agent.md` 2절)이 여기서도 그대로 적용된다 — 재구성 시 새 팀에 넘어가는 것은 **파일뿐**이고, 이전 팀의 대화·추론은 넘어가지 않으며 넘길 필요도 없다.

## 3. 팀 데이터 전달 — 태스크 기반·메시지 기반 상세

`multi-agent.md` 10절의 데이터 전달 프로토콜 표 중 팀 모드 전용 두 행의 상세다. 나머지 두 행(파일 기반·반환값 기반)과 공통 금지 사항은 그 표에 있다.

| 전략 | 방식 | 무엇에 쓰는가 |
|---|---|---|
| **태스크 기반** | `TaskCreate`/`TaskUpdate`로 작업 상태 공유 | 진행 상황, 의존 관계, 작업 자체 요청(claim) |
| **메시지 기반** | `SendMessage`로 팀원 간 직접 통신 | **조율 신호에 한정** — "X 완료, 경로는 여기", "Y 상충 발견, 확인 바람" |

**팀 모드 권장 조합:** 파일 기반(산출물·증거) + 태스크 기반(조율) + 메시지 기반(신호만). 산출물 본문을 `SendMessage`로 실어 나르지 않는다 — 그러면 모든 수신자의 컨텍스트가 남의 중간 추론으로 채워지고, 그것이 정확히 논문 §XVII(다중 에이전트)가 경고한 오염이다. 태스크 기반은 **상태**를, 메시지 기반은 **사건**을, 파일 기반은 **내용**을 나른다. 셋의 역할이 섞이는 순간(태스크 description에 결과 본문을 적거나, 메시지로 원문을 보내거나) 팀 모드의 유일한 이점인 조율이 오염 비용으로 상쇄된다.

## 4. 에이전트 정의의 팀 통신 프로토콜 절

에이전트 정의 파일의 필수 섹션(핵심 역할 / 작업 원칙 / 입력·출력 프로토콜 / 핸드오프 / 에러 핸들링 / 협업)은 `multi-agent.md` 7절에 있다. **팀 모드면 여기에 `## 팀 통신 프로토콜` 절을 추가한다.** 이 절은 대상별로 다음 셋을 명시한다 — "필요하면 소통하라"가 아니라 **누구에게·언제·무엇을**이 적혀 있어야 한다.

| 항목 | 무엇을 적는가 |
|---|---|
| 발신 | 어떤 사건이 확정되면 **누구에게** `SendMessage`를 보내는가. 보내는 것은 본문이 아니라 "무엇이 어디에 생겼다"는 신호다 |
| 수신 | **누구로부터** 어떤 보고를 받는가, 받은 뒤 무엇을 하는가 — 특히 **수정 권한이 누구에게 있는지**(검증자의 보고를 받아도 수정은 생산자가 한다) |
| 브로드캐스트 | 이미 넘긴 산출물을 변경했을 때 **변경 사실만** 알릴 대상 |

작성 실례는 8절 `worldbuilder.md`의 `## 팀 통신 프로토콜` 절이다.

## 5. 오케스트레이터 템플릿 A — 에이전트 팀 모드

오케스트레이터는 팀 전체를 조율하는 상위 스킬이자 **라우터**다. Phase 0(컨텍스트 확인)과 Phase 1(준비)은 전 모드 공통이므로 `multi-agent.md` 13.1·13.2절을 그대로 쓴다. 오케스트레이터 작성 원칙 5개도 `multi-agent.md` 13절 말미에 있다.

````markdown
---
name: {domain}-orchestrator
description: "{도메인} 에이전트 팀을 조율하는 오케스트레이터. {초기 실행 키워드}. 후속 작업: {도메인} 결과 수정, 부분 재실행, 업데이트, 보완, 다시 실행, 이전 결과 개선 요청 시에도 반드시 이 스킬을 사용."
---
# {Domain} Orchestrator
## 실행 모드: 에이전트 팀
## 에이전트 구성
| 팀원 | 타입 | model | 역할 | 스킬 | 출력 |
|---|---|---|---|---|---|
| {teammate-1} | {커스텀/빌트인} | {최소 모델} | {역할} | {skill} | `_workspace/{phase}_{teammate-1}_{artifact}.md` |
## Phase 0: 컨텍스트 확인 (후속 작업 지원)
`multi-agent.md` 13.1절의 `_workspace/` 3분기(초기 실행 / 부분 재실행 / 새 실행)를 그대로 수행한다.
## Phase 1: 준비
`multi-agent.md` 13.2절과 동일 — 사용자 입력 분석 → `_workspace/` 생성 → 입력을 `_workspace/00_input/`에 저장.
## Phase 2: 팀 구성
```
TeamCreate(team_name: "{domain}-team", members: [
  { name: "{teammate-1}", agent_type: "{type}", model: "{최소 모델}", prompt: "{역할·작업 지시}" },
])
TaskCreate(tasks: [
  { title: "{작업1}", description: "{상세}", assignee: "{teammate-1}" },
  { title: "{작업3}", description: "{상세}", depends_on: ["{작업1}"] },
])
```
> 팀원당 5~6개 작업이 적정(1절). 의존 작업은 `depends_on`으로 명시.
## Phase 3: {주요 작업}
팀원들이 공유 작업 목록에서 작업을 claim해 독립 수행한다. 산출물은 `_workspace/{phase}_{agent}_{artifact}.md`에 저장하고 `SendMessage`는 조율 신호만 나른다(3절). 리더는 유휴 알림 수신 / `TaskGet` 진행률 확인 / 막힌 팀원 재지시·재할당.
## Phase 4: 검증과 통합
`TaskGet`으로 완료 확인 → 각 산출물 `Read` → **독립 검증자**(Edit/Write 없음)가 검증하고 실패 증거는 라우터를 거쳐 생산자에게 반송(`multi-agent.md` 8절) → 최종 산출물 `{output-path}/{filename}` 생성, 미검증 항목은 표식과 함께 명시.
## Phase 5: 정리
팀원 종료 요청 → `TeamDelete` → `_workspace/`의 산출물 아티팩트 보존(체크포인트는 최신 1개만) → 결과 요약 보고(미해결 항목 포함).
## 데이터 흐름
```
[리더] → TeamCreate → [teammate-1] ←신호(SendMessage)→ [teammate-2]
            _workspace/01_t1_a.md          _workspace/01_t2_b.md
                        └────── Read ──────────┘
              [검증자: 읽기 전용] → 실패 증거 → [리더: 통합] → 최종 산출물
```
## 에러 핸들링 / 테스트 시나리오
`multi-agent.md` 11절의 3문장과 상황별 전략표를 그대로 포함한다. 시나리오는 정상 1 + 에러 1 이상. **정상:** 입력 → 분석 → 팀 구성(N명/M작업) → 자체 조율 → 검증·통합 → 정리 → `{output-path}/{filename}` 생성. **에러:** Phase 3에서 {teammate-2} 중지 → 유휴 알림 → 상태 확인·재시작 → 실패 시 재할당 → 나머지로 진행 → 보고서에 "{teammate-2} 영역 일부 미수집" 명시.
````

## 6. 오케스트레이터 템플릿 C — 하이브리드 모드

Phase마다 성격이 확연히 다를 때 팀과 서브를 섞는다. 팀이 한 Phase라도 등장하므로 이 템플릿은 팀 모드의 제약(세션당 1팀, 중첩 불가)을 그대로 상속한다.

| Phase | 모드 | 이유 |
|---|---|---|
| 병렬 수집 | 서브 에이전트 | 독립 자료 수집, 팀 통신 불필요 |
| 합의 통합 | 에이전트 팀 | 상충 데이터 토론·합의 필요 |
| 독립 검증 | 서브 에이전트 | 검증자 1명이 격리 상태에서 객관 검증 |

**전환 규칙:** 팀→서브는 반드시 `TeamDelete` 후 `Agent` 호출. 서브→팀은 서브의 파일 산출물 경로를 팀원에게 전달. 팀→팀은 이전 팀 정리 후 새 `TeamCreate`(세션당 1팀만 활성, 2절).

## 7. 팀 통신 패턴 실례

### 리서치 팀 (팬아웃/팬인)
```
official ──신호──→ background   (관련 공식 발표가 나왔다, 경로 X)
media ────신호──→ background   (투자/인수 정보 확인, 경로 Y)
community ─신호──→ media        (커뮤니티 반응 중 미디어 관련 항목)
모든 팀원 ──TaskUpdate──→ 공유 작업 목록   (진행률)
리더 ←──── 유휴 알림 ──── 완료된 팀원     (자동)
```
본문은 항상 `_workspace/02_{agent}_raw.md`에 있고 메시지는 "어디에 무엇이 생겼다"만 나른다. 리더는 4개 산출물을 `Read`해 통합하며 상충 정보는 출처를 병기한다.

### 코드 리뷰 팀 (팬아웃/팬인 + 토론)
```
security ────신호──→ performance  ("이 SQL 주입 가능, 성능 측면 확인 요청")
performance ─신호──→ test         ("N+1 쿼리 발견, 관련 테스트 존재 여부 확인 요청")
test ────────신호──→ security     ("인증 모듈 테스트 없음, 보안 우선순위 의견 요청")
```
핵심은 리뷰어들이 **리더를 거치지 않고** 직접 소통해 교차 영역 이슈를 빠르게 잡는 것이다. 단, 각 리뷰어는 읽기 전용이며 코드를 고치지 않는다(`multi-agent.md` 8절).

### 감독자 패턴 — 코드 마이그레이션 팀
```
[supervisor/리더] → 파일 목록 분석 → 복잡도 추정 → TaskCreate로 배치 등록
    ├→ [migrator-1] (batch A)   ← 팀원이 자체 claim
    ├→ [migrator-2] (batch B)
    └→ [migrator-3] (batch C)
    ← TaskUpdate 수신 → 성공이면 다음 배치 자동 할당 / 실패면 원인 확인 후 재할당
    → 전 작업 완료 → 리더가 통합 테스트(계산적 센서) 실행
```
팬아웃과의 차이: 작업이 사전 고정이 아니라 **런타임에 동적으로 할당**된다.

## 8. 실물 예시 — 생산자 에이전트 정의 파일 전문

`worldbuilder.md` (SF 소설 팀 — 파이프라인 + 팬아웃). 팀 통신 프로토콜 절(4절)을 가진 생산자 에이전트의 전문이다. 검증자 쪽 실물 예시(`webtoon-reviewer.md`, 쓰기 권한 없음)는 `multi-agent.md` 15절에 있다.

```markdown
---
name: worldbuilder
description: "SF 소설의 세계관을 구축하는 전문가. 물리 법칙, 사회 구조, 기술 수준, 역사를 설계한다."
model: {작업에 맞는 최소 모델}
maxTurns: 3
---
# Worldbuilder — SF 세계관 설계 전문가

당신은 SF 소설의 세계관 설계 전문가입니다. 과학적 사실에 기반하되 상상력을 확장하여, 이야기가 펼쳐질 세계의 물리적·사회적·기술적 토대를 구축합니다.

## 핵심 역할
1. 세계의 물리 법칙과 기술 수준 정의
2. 사회 구조, 정치 체계, 경제 시스템 설계
3. 역사적 맥락과 현재 갈등 구조 수립
4. 장소별 환경과 분위기 묘사

## 작업 원칙
- 내적 일관성 최우선 — 설정 간 모순이 없어야 한다
- "만약 이 기술이 있다면?" 연쇄 질문으로 세계의 파급 효과를 추론
- 이야기에 봉사하는 세계관 — 플롯을 방해하는 과도한 설정은 지양

## 입력/출력 프로토콜
- 입력: 사용자의 세계관 컨셉, 장르 요구사항
- 출력: `_workspace/01_worldbuilder_setting.md`
- 형식: 마크다운. 섹션별 (물리/사회/기술/역사/장소)

## 핸드오프
`## HANDOFF` 6필드로 character-designer·plot-architect에게 전달한다. 아티팩트 포인터는 위 출력 경로, 가정에는 확정되지 않은 설정을, 기한에는 다음 단계 착수까지 남은 예산을, 미해결에는 미결정 항목을 적는다.

## 팀 통신 프로토콜
- character-designer에게: 사회 구조·계급·직업군이 확정됐다는 **신호**를 SendMessage (본문은 파일로)
- plot-architect에게: 주요 갈등 구조가 확정됐다는 신호를 SendMessage
- science-consultant로부터: 과학적 오류 **보고**를 수신 → 설정은 생산자인 내가 직접 수정
- 세계관을 변경하면 관련 팀원에게 변경 사실만 브로드캐스트

## 에러 핸들링
- 컨셉이 모호하면 3가지 방향을 제안하고 선택을 요청한다 (에스컬레이션 패킷 형식)
- 과학적 오류 지적을 받으면 대안을 함께 제시하고 수정 이력을 산출물에 남긴다
- 1회 재시도 후 재실패한 영역은 미해결 항목으로 명시하고 진행한다

## 협업
- character-designer·plot-architect에게 설정 정보를 제공하고, science-consultant의 검증 결과를 반영하되 수정은 항상 생산자인 내가 한다
```

## 9. 팀 모드 검증 체크리스트

`multi-agent.md` 18절의 공통 체크리스트에 **더해** 팀 모드에서만 확인한다.

- [ ] 오케스트레이터 최상단에 **실행 모드: 에이전트 팀**이 명시됨 (하이브리드면 Phase별 모드 표 첨부, 6절)
- [ ] 팀원 수와 팀원당 작업 수가 1절 가이드라인 범위 안 — 조율 시간이 작업 시간을 넘지 않음
- [ ] **모든 팀원 정의에 `model` 파라미터 명시** (특정 모델 강제가 아니라 명시성)
- [ ] 팀 모드 에이전트 정의에 `## 팀 통신 프로토콜` 절 존재 — 발신·수신·브로드캐스트 대상이 이름으로 적힘 (4절)
- [ ] `SendMessage`가 조율 신호만 나름 — 산출물 본문이 메시지·태스크 description으로 흐르지 않음 (3절)
- [ ] 의존 작업에 `depends_on` 명시, 진행 지연 시 `TaskGet`→`TaskUpdate` 복구 경로 존재
- [ ] Phase 5에 `TeamDelete`와 산출물 보존 절차 존재, Phase 간 재구성은 파일 저장 → `TeamDelete` → 새 `TeamCreate` 순서 (2절)
- [ ] 세션당 1팀 제약 위반 없음 — 중첩 팀 없음, 계층적 위임은 2단계 이내로 평탄화
- [ ] 검증자는 팀 안에서도 읽기 전용이며 리더를 거쳐 실패 증거를 반송 (`multi-agent.md` 8절)
